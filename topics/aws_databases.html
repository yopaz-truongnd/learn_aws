🗄️ 1. Amazon RDS & RDS Custom 🗄️ 1. Amazon RDS & RDS Custom
Amazon RDS (4 tiêu chí)Amazon RDS (4-Point Summary) • Là gì: Dịch vụ CSDL quan hệ (SQL) quản lý hoàn toàn cho 6 engines: PostgreSQL, MySQL, MariaDB, Oracle, MS SQL Server, IBM Db2.
• Dùng khi nào: Chạy RDBMS với chi phí vận hành tối thiểu (least operational overhead), tự động vá lỗi, sao lưu Point-in-Time và Multi-AZ.
• Khác gì dịch vụ gần giống: Read Replicas (tối đa 15, Async) dùng để Scale Reads; Multi-AZ (Sync) dùng cho HA / DR (Standby không đọc được).
• Điểm hay hỏi: Automated Backups tối đa 35 ngày. Nhân bản Read Replica cùng Region là MIỄN PHÍ (Cross-Region tính phí). • What is it: Fully managed relational SQL database supporting PostgreSQL, MySQL, MariaDB, Oracle, MS SQL Server, IBM Db2.
• When to use: Managed RDBMS with least operational overhead, automated patching, PITR backups, and Multi-AZ HA.
• Differences: Read Replicas (up to 15, Async) for Read Scaling; Multi-AZ (Sync) for HA / DR.
• Hotspots: Automated Backups up to 35 days. Same-Region Read Replica replication is FREE.
Amazon RDS Custom (4 tiêu chí)Amazon RDS Custom (4-Point Summary) • Là gì: Phiên bản RDS cho phép quyền OS Admin / SSH / RDP vào máy chủ bên dưới.
• Dùng khi nào & Giới hạn: Chỉ hỗ trợ 2 engines duy nhất: Oracle và Microsoft SQL Server khi ứng dụng đóng gói cần can thiệp OS/cài custom patches (nhớ bật Pause Automation Mode tối đa 24h). • What is it: Managed RDS variant granting full underlying OS root/SSH/RDP access.
• When to use & Limits: Exclusively supports Oracle and Microsoft SQL Server for legacy apps requiring OS customization (pause automation up to 24h).
⚡ 2. Amazon Aurora & RDS Proxy ⚡ 2. Amazon Aurora & RDS Proxy
Amazon Aurora (4 tiêu chí)Amazon Aurora (4-Point Summary) • Là gì: CSDL đám mây độc quyền của AWS tương thích MySQL & PostgreSQL, nhanh gấp 5x MySQL và 3x Postgres.
• Dùng khi nào: CSDL quan hệ cấp doanh nghiệp cần tự mở rộng dung lượng (10 GB → 128 TB), Failover < 30s, hoặc Aurora Global Database (< 1s lag).
• Khác gì RDS thường: Lưu 6 bản sao trên 3 AZs (4/6 ghi, 3/6 đọc); tối đa 15 Replicas dùng chung Shared Storage thông qua Reader Endpoint.
• Điểm hay hỏi: Aurora Cloning (Copy-on-Write) tạo bản sao DB staging cực nhanh không cần copy dữ liệu thật. • What is it: AWS cloud-native RDBMS compatible with MySQL & PostgreSQL (5x/3x faster).
• When to use: Enterprise SQL needing auto-expanding storage (10 GB → 128 TB), instant failover, or Aurora Global DB (<1s lag).
• vs RDS: Stores 6 copies across 3 AZs; up to 15 Replicas sharing storage via a single Reader Endpoint.
• Hotspots: Aurora Cloning uses Copy-on-Write for instant staging clones.
Amazon RDS Proxy (4 tiêu chí)Amazon RDS Proxy (4-Point Summary) • Là gì: Dịch vụ quản lý và gom nhóm kết nối DB (Managed Connection Pooling) cho RDS/Aurora.
• Dùng khi nào & Điểm hay hỏi: Ngăn AWS Lambda làm tràn kết nối DB (Too many connections), giảm tới 66% thời gian Failover, ép buộc IAM Authentication + Secrets Manager, chỉ truy cập nội bộ trong VPC. • What is it: Fully managed serverless Database Connection Pooling proxy for RDS/Aurora.
• When to use & Hotspots: Prevents AWS Lambda connection exhaustion, reduces failover time by up to 66%, enforces IAM Auth + Secrets Manager, strictly VPC-private.
🧠 3. Amazon ElastiCache (Redis vs Memcached) 🧠 3. Amazon ElastiCache (Redis vs Memcached)
Là gì & Dùng khi nàoWhat is it & When to use • Là gì: Dịch vụ cơ sở dữ liệu bộ nhớ đệm trên RAM (Managed In-Memory Cache) với độ trễ sub-millisecond.
• Dùng khi nào: Giảm tải đọc lặp lại cho RDS/Aurora (Cache-Aside / Lazy Loading), lưu trữ phiên đăng nhập (Stateless User Session Store), hoặc làm bảng xếp hạng (Gaming Leaderboards). • What is it: Managed In-Memory Data Store & Cache delivering sub-millisecond latency.
• When to use: Offload repetitive RDS reads (Lazy Loading), store Stateless User Sessions, or power real-time Gaming Leaderboards.
Khác gì dịch vụ gần giống & Điểm hay bị hỏiDifferences & Exam Hotspots • Redis vs Memcached: Redis có Multi-AZ Auto-Failover, Read Replicas, Backup/Restore (AOF), và Sorted Sets (Leaderboards); Memcached là bộ đệm đa luồng phân mảnh (Sharding) đơn giản, KHÔNG có HA, KHÔNG có Backup.
• ElastiCache vs DAX: Dùng DAX nếu cache riêng cho DynamoDB; dùng ElastiCache cho RDS/Aurora, Session Store, hoặc Leaderboards. • Redis vs Memcached: Redis supports Multi-AZ Auto-Failover, Read Replicas, Backups, and Sorted Sets (Leaderboards); Memcached is multi-threaded sharded cache with NO HA and NO persistence.
• ElastiCache vs DAX: Use DAX exclusively for DynamoDB; use ElastiCache for RDS/Aurora, Sessions, or Leaderboards.

2. Chủ đề kinh điển: RDS Multi-AZ vs Read Replicas 2. The Canonical Topic: RDS Multi-AZ vs Read Replicas
Phân biệt rạch ròi giữa mục tiêu Kháng lỗi (Disaster Recovery) và mục tiêu Mở rộng đọc (Scale Reads) Clear distinction between Disaster Recovery (High Availability) and Scaling Read Performance
Tiêu chí so sánh RDS Multi-AZ (Kháng lỗi / DR) RDS Read Replicas (Mở rộng đọc)
Mục đích cốt lõi (Primary Purpose) Tính sẵn sàng cao (High Availability) & Khôi phục sự cố (DR). Không có tác dụng mở rộng hiệu năng đọc! Mở rộng quy mô đọc (Scalability for Read-heavy workloads). Giải tỏa tải truy vấn SELECT cho Master DB.
Cơ chế đồng bộ (Replication) Đồng bộ (Synchronous): Giao dịch chỉ xác nhận thành công (Commit) khi dữ liệu đã ghi xong ở cả 2 AZ. Đảm bảo Zero Data Loss. Bất đồng bộ (Asynchronous): Master ghi xong trả về ngay, dữ liệu chuyển dần sang bản sao. Chấp nhận có độ trễ (Replication Lag).
Khả năng truy xuất (Access) Bản sao Standby DB ở AZ phụ là Passive (Không cho phép đọc hay ghi). Chỉ dùng để chờ sẵn khi xảy ra sự cố. Bản sao Read Replica là Active (Chỉ cho phép đọc - Read Only). Có chuỗi kết nối DNS Endpoint riêng biệt để ứng dụng kết nối đọc.
Cơ chế chuyển đổi dự phòng (Failover) Tự động 100% (Automatic Failover) trong 60–120 giây. AWS tự động chuyển DNS Endpoint trỏ sang Standby DB. Ứng dụng không cần đổi Connection String! Không tự động. Khi Master sập, bạn phải kích hoạt thủ công lệnh Promote Read Replica để biến nó thành Standby hoặc Master độc lập.
Phạm vi địa lý (Scope) Trong Cùng 1 Region (Khác Availability Zone). Có thể đặt trong cùng AZ, khác AZ, hoặc Khác Region (Cross-Region Read Replica) phục vụ giảm độ trễ cho người dùng toàn cầu.
Số lượng bản sao (Capacity) Chỉ 1 Standby DB (hoặc 2 với Multi-AZ Cluster mới). Tối đa 15 Read Replicas cho mỗi database master.

💡 Mẹo phòng thi SAA-C03 (Exam Tip): Phân biệt Important Port vs RDS Port & Security Group Chaining 💡 SAA-C03 Exam Tip: Differentiating Important vs Database Ports & Security Group Chaining
• Không cần học vẹt: Đề thi SAA-C03 không yêu cầu bạn nhớ lòng từng cổng mạng. Bạn chỉ cần phân biệt rõ ràng giữa Cổng Web/Admin (Port 80, 443, 22) với Cổng Cơ sở dữ liệu (Port 5432, 3306, 1433, 1521).
• Bẫy đề thi kinh điển: Khi cấu hình Security Group Inbound Rule cho RDS, đáp án đúng LUÔN là mở đúng Database Port (ví dụ MySQL 3306 hoặc PostgreSQL 5432) và Source là Security Group ID của App/Web Server (sg-xxxx). Bất kỳ đáp án nào mở Port 80/443 trên RDS hoặc đặt Source là 0.0.0.0/0 đều là ĐÁP ÁN SAI!
• No need to memorize rote numbers: SAA-C03 will not test you on port numbers in isolation. You only need to differentiate an Important Port (Web/Admin: 80, 443, 22) from an RDS Database Port (PostgreSQL 5432, MySQL 3306, etc.).
• Classic Exam Trap: When configuring an Inbound Rule for an RDS Security Group, the correct answer ALWAYS allows the Database Port (e.g. MySQL 3306 or PostgreSQL 5432) with Source set to the App/Web Security Group ID (sg-xxxx). Any choice opening Port 80/443 on RDS or allowing 0.0.0.0/0 is strictly INCORRECT!

3. Kiến trúc đột phá của Amazon Aurora 3. Amazon Aurora Cloud-Native Architecture
Tách biệt tầng tính toán (Compute) và tầng lưu trữ phân tán dùng chung (Shared Storage) Decoupled compute and shared distributed storage across three availability zones
Kiến trúc lưu trữ 6 bản sao trên 3 AZ
• Aurora lưu trữ dữ liệu thành các khối 10 GB phân tán trên 3 Availability Zones, mỗi AZ giữ 2 bản sao → Tổng cộng 6 bản sao (6 copies).
• Khả năng chịu lỗi phi thường: Vẫn ghi được bình thường nếu mất 2 bản sao (cần 4/6 quorum để ghi), và vẫn đọc được bình thường nếu mất 3 bản sao (cần 3/6 quorum để đọc).
• Cơ chế tự phục hồi (Self-Healing): Tự động sửa chữa các khối hỏng ở mức block nền mà không ảnh hưởng người dùng.
• Dung lượng lưu trữ tự động mở rộng từ 10 GB lên đến 128 TiB theo bước nhảy 10 GB mà không cần phân bổ trước.
• Data is striped into 10 GB segments replicated across 3 Availability Zones with 2 copies per AZ → 6 copies total.
• Extreme Fault Tolerance: Handles loss of 2 copies without affecting writes (4/6 quorum), and loss of 3 copies without affecting reads (3/6 quorum).
• Self-healing storage constantly scans and repairs corrupted disk blocks.
• Storage automatically expands up to 128 TiB dynamically in 10 GB increments without provisioning.
Endpoints & Aurora Read Replicas
• Writer Endpoint: Địa chỉ DNS luôn trỏ chính xác về Instance Master hiện tại (hỗ trợ đọc và ghi).
• Reader Endpoint: Địa chỉ DNS tự động cân bằng tải phân phối các kết nối đọc (SELECT) đều ra toàn bộ các bản sao Read Replicas.
• Hỗ trợ tối đa tới 15 Aurora Read Replicas với độ trễ đồng bộ cực thấp (Replication lag < 10ms) vì tất cả các replica đều dùng chung tầng Shared Storage ngầm.
• Hỗ trợ Auto-scaling Replicas: Tự động thêm replica khi tải CPU đọc tăng cao.
• Writer Endpoint: Canonical DNS pointing strictly to current Master DB instance.
• Reader Endpoint: DNS endpoint load balancing read connections evenly across all active Read Replicas.
• Up to 15 Aurora Read Replicas with near-zero replication lag (<10ms) thanks to shared storage fabric.
• Supports Auto-scaling Replicas triggered by average CPU or connection thresholds.
Aurora Serverless v2
• Tự động co giãn tài nguyên CPU & RAM tức thì chỉ trong vài phần trăm giây dựa trên nhu cầu thực tế của ứng dụng.
• Đo lường bằng đơn vị ACU (Aurora Capacity Units): 1 ACU = 2 GiB RAM kèm tỷ lệ CPU tương ứng.
• Lý tưởng cho các tải công việc khó đoán trước, các ứng dụng doanh nghiệp ít dùng ban đêm hoặc các hệ thống SaaS đa khách hàng (Multi-tenant).
• Scales compute capacity in fractions of a second dynamically to match instantaneous workload bursts.
• Measured in fine-grained ACUs (Aurora Capacity Units): 1 ACU = 2 GiB RAM with matched CPU.
• Ideal for unpredictable spiky traffic, infrequent off-hours apps, and multi-tenant SaaS environments.
Aurora Global Database, Backtrack & Cloning
• Aurora Global Database: 1 Primary Region + tối đa 5 Secondary Regions (Read Only), độ trễ đồng bộ < 1 giây, khôi phục thảm họa (DR) với RTO < 1 phút.
• Aurora Cloning (Copy-on-Write): Tạo bản sao DB Staging/Testing từ Production nhanh hơn và rẻ hơn rất nhiều so với Snapshot Restore vì ban đầu dùng chung tầng lưu trữ và chỉ tách block khi có dữ liệu ghi mới.
• Aurora Custom Endpoints: Định nghĩa một Endpoint riêng trỏ tới nhóm các Aurora Replicas cấu hình lớn để chuyên chạy báo cáo phân tích (Analytical queries).
• Aurora Global Database: 1 Primary Region + up to 5 Secondary Regions (Read Only) with <1s replication lag and RTO <1m.
• Aurora Cloning (Copy-on-Write): Creates fast, cost-effective staging/test clones from Production without physically duplicating storage blocks upfront.
• Aurora Custom Endpoints: Isolates a subset of larger Aurora Replicas dedicated to analytical queries.

4. Chuyên sâu Amazon DynamoDB (NoSQL Serverless) 4. Amazon DynamoDB Deep Dive
Cấu trúc khóa chính, chế độ thông lượng, bộ đệm DAX, Global Tables và xử lý sự kiện Streams Primary key architecture, capacity modes, DAX accelerator, Global Tables, and DynamoDB Streams
🔑 Thiết kế Primary Keys 🔑 Primary Key Design
Partition Key thuần (HASH) Bảng chỉ gồm 1 thuộc tính khóa chính duy nhất. DynamoDB băm (hash) giá trị này để quyết định dữ liệu được lưu trên phân vùng vật lý (Physical Partition) nào. Phải có tính phân tán cao (High Cardinality). Table key consisting of a single attribute. DynamoDB hashes this value to determine the physical storage partition. Must have high cardinality to avoid hot partitions.
Composite Key (HASH + RANGE) Kết hợp Partition Key (Băm) và Sort Key (Sắp xếp). Ví dụ: `UserID` (Partition Key) + `GameID` (Sort Key). Cho phép truy vấn tất cả các game của 1 người dùng theo thứ tự thời gian. Combination of Partition Key (Hash) and Sort Key (Range). Allows 1:many groupings, querying all items for a given partition key sorted sequentially.
Chỉ mục phụ (LSI vs GSI) • Local Secondary Index (LSI): Cùng Partition Key, đổi Sort Key khác. Chỉ tạo được lúc tạo bảng ban đầu.
• Global Secondary Index (GSI): Đổi cả Partition Key và Sort Key mới. Có thể tạo hoặc xóa bất kỳ lúc nào sau này. • Local Secondary Index (LSI): Same partition key, different sort key. Defined only at table creation.
• Global Secondary Index (GSI): Completely new partition and sort key. Can be added or deleted anytime.
⚡ Chế độ thông lượng & DAX ⚡ Throughput & DAX Caching
Provisioned vs On-Demand Capacity • Provisioned: Bạn đặt trước RCU (Read Capacity Unit) và WCU (Write Capacity Unit). Có hỗ trợ Auto-scaling. Tiết kiệm chi phí khi tải đều đặn.
• On-Demand: Tự động co giãn theo từng request, không cần dự đoán tải. Lý tưởng cho tải đột biến, khó lường hoặc ứng dụng mới. • Provisioned: Pre-allocate RCUs and WCUs backed by auto-scaling. Cost-effective for predictable workloads.
• On-Demand: Pay-per-request model with zero capacity planning. Best for unpredictable or spiky traffic.
DynamoDB Accelerator (DAX) Cụm cache phần cứng In-Memory đặt ngay trước DynamoDB. Giảm độ trễ đọc từ mili-giây (ms) xuống micro-giây (Microseconds - μs). Tương thích 100% với SDK hiện có của DynamoDB, không cần viết lại mã nguồn ứng dụng! Dedicated hardware in-memory caching cluster for DynamoDB. Slashes read latencies from milliseconds down to microseconds (μs). 100% API-compatible, requires zero application code rewrite!
🌐 Tính năng nâng cao 🌐 Advanced Capabilities
DynamoDB Global Tables Nhân bản dữ liệu 2 chiều đa vùng Multi-Region, Multi-Active (Active-Active). Cho phép ghi và đọc ở bất kỳ Region nào với độ trễ dưới 1 giây. Xử lý xung đột ghi theo nguyên tắc Last Writer Wins. Multi-Region, Multi-Active fully replicated tables. Enables local reads and writes across multiple regions with <1 second replication. Resolves conflicts via Last Writer Wins.
DynamoDB Streams & TTL • DynamoDB Streams: Nhật ký ghi lại mọi thay đổi (Insert, Update, Delete) lưu trong 24 giờ. Tích hợp trực tiếp với AWS Lambda để tạo kiến trúc Event-Driven phản ứng tức thì.
• Time To Live (TTL): Tự động xóa các bản ghi hết hạn sau một mốc thời gian Unix Timestamp mà hoàn toàn không tính phí WCU! • DynamoDB Streams: 24-hour changelog of item modifications. Directly triggers AWS Lambda for event-driven workflows.
• Time To Live (TTL): Automatically purges expired items without consuming Write Capacity Units (WCU)!

📐 Chiến lược nạp dữ liệu vào Cache 📐 Caching Architectural Patterns
Lazy Loading (Cache-Aside) Ứng dụng đọc từ Cache trước. Nếu không có (Cache Miss), đọc từ Database rồi mới ghi kết quả vào Cache. Ưu điểm: Chỉ nạp đúng dữ liệu cần. Nhược điểm: Dữ liệu trong Cache có nguy cơ bị cũ (Stale Data), cần kết hợp thời gian sống TTL. App checks cache first. On miss, reads from DB and populates cache. Pros: Only caches requested data. Cons: Stale data vulnerability, requires strict TTL expiration.
Write-Through (Ghi đồng thời) Mỗi khi có thao tác ghi dữ liệu, ứng dụng ghi đồng thời vào cả Database và Cache. Ưu điểm: Dữ liệu trong Cache luôn tươi mới 100%. Nhược điểm: Tốn tài nguyên RAM vì lưu cả những dữ liệu có thể không bao giờ được đọc lại (Cache Churn). App updates cache and DB concurrently on every write. Pros: Zero stale data. Cons: Higher write latency and memory churn caching unrequested writes.

6. Các bẫy & Kịch bản đề thi thường gặp (SAA-C03 Exam Traps) 6. Common Exam Traps & Scenarios (SAA-C03)
Những điểm mấu chốt đề thi phân biệt giữa các giải pháp cơ sở dữ liệu Critical discrimination criteria frequently tested in database scenarios
Bẫy: Báo cáo Analytics làm nghẽn Database giao dịch
• Tình huống: Ban giám đốc chạy báo cáo phân tích nặng (Heavy Reporting/Analytics) vào ban ngày khiến Database giao dịch chính của khách hàng bị treo hoặc phản hồi chậm.
• Bẫy: Bật Multi-AZ là SAI (vì Standby DB là Passive, không thể trỏ câu lệnh SELECT vào Standby được).
• Đáp án chuẩn: Tạo một RDS Read Replica và cấu hình ứng dụng báo cáo chỉ kết nối vào chuỗi kết nối riêng của Read Replica này!
• Scenario: Heavy reporting analytics executed during peak hours causes severe latency on primary transactional DB.
• Trap: Enabling Multi-AZ does NOT solve this (Standby DB is passive and rejects client read queries).
• Canonical Solution: Spin up an RDS Read Replica and point reporting workloads strictly to the replica endpoint!
Amazon RDS Proxy & Cạn kiệt Connection Pool
• Tình huống: Hàng nghìn hàm AWS Lambda chạy đồng thời kết nối vào RDS khiến Database bị cạn kiệt Connection Pool và crash.
• Giải pháp: Triển khai Amazon RDS Proxy ở giữa Lambda và RDS. RDS Proxy quản lý chia sẻ Connection Pool thông minh, giảm thời gian chuyển đổi dự phòng (Failover) xuống 66% và bắt buộc xác thực bảo mật IAM.
• Scenario: Spikes of concurrent serverless AWS Lambda executions exhaust RDS database connection pools, crashing backend.
• Solution: Place Amazon RDS Proxy in front of RDS. Pools and reuses DB connections, cuts failover time by 66%, and enforces IAM authentication.
Lỗi ProvisionedThroughputExceededException trên DynamoDB
• Xảy ra khi số lượng request đọc/ghi vượt quá mức RCU/WCU đã cấp phát, hoặc do hiện tượng Hot Partition (quá nhiều dữ liệu dồn vào 1 Partition Key duy nhất).
• Cách xử lý chuẩn trong đề thi:
  1. Dùng cơ chế Exponential Backoff khi retry trong ứng dụng.
  2. Phân bổ lại Partition Key có độ phân tán cao hơn (High Cardinality).
  3. Gắn thêm DynamoDB Accelerator (DAX) để giải tỏa các request đọc lặp lại.
• Occurs when traffic exceeds provisioned RCU/WCU or a Hot Partition forms around an unevenly distributed partition key.
• Canonical Exam Fixes:
  1. Implement Exponential Backoff retries.
  2. Redesign partition keys for higher cardinality.
  3. Introduce DAX accelerator to absorb repeated read bursts.
Khôi phục thảm họa xuyên Region (Cross-Region DR) cho RDS
• Muốn có kế hoạch phòng chống thảm họa cho RDS khi toàn bộ 1 Region bị sập:
• Phương án 1 (Chi phí thấp): Tự động sao lưu Snapshot và chạy script copy snapshot sang Region khác định kỳ.
• Phương án 2 (RTO & RPO cực thấp): Tạo Cross-Region Read Replica ở Region thứ hai. Khi Region chính gặp nạn, kích hoạt (Promote) Read Replica này lên thành Master độc lập chỉ trong vài phút.
• Mitigating catastrophic whole-region outages for RDS databases:
• Option 1 (Cost-optimized): Automated snapshots copied across regions asynchronously.
• Option 2 (Low RPO/RTO): Maintain a Cross-Region Read Replica in secondary region. Promoted to standalone production master within minutes upon disaster.

7. Nguyên tắc vàng khi làm bài thi (SAA-C03 Golden Rules) 7. SAA-C03 Database Golden Rules
Quy tắc loại trừ đáp án siêu tốc cho phần cơ sở dữ liệu Essential axioms to rapidly eliminate incorrect database choices
  • 1
    RDS Multi-AZ là cho Sẵn sàng cao (HA), KHÔNG PHẢI để tăng tốc độ đọc RDS Multi-AZ is strictly for High Availability, NEVER for Read Scaling Tuyệt đối không chọn Multi-AZ khi đề bài yêu cầu giải quyết nghẽn hiệu năng đọc (Read Performance bottleneck). Standby DB trong Multi-AZ là Passive và từ chối mọi kết nối client. Muốn tăng tốc đọc → Bắt buộc chọn Read Replicas hoặc ElastiCache. Never choose Multi-AZ when answering read performance issues. Standby DB instances in Multi-AZ reject all direct client traffic. To scale reads → Always choose Read Replicas or ElastiCache.
  • 2
    Yêu cầu NoSQL Serverless độ trễ mili-giây đơn vị → Luôn chọn Amazon DynamoDB Serverless NoSQL with single-digit millisecond latency → Always choose DynamoDB Bất kỳ kịch bản nào đòi hỏi khả năng co giãn vô hạn, không cần quản trị máy chủ, dữ liệu dạng Key-Value / JSON và độ trễ dưới 10ms, DynamoDB luôn là đáp án số 1. Nếu cần xuống cấp độ micro-giây (μs) → Kết hợp thêm DAX. When requirements specify serverless operations, unbounded horizontal scale, and <10ms access for JSON/Key-Value data, DynamoDB is the definitive choice. For microsecond scale → Add DAX.
  • 3
    Aurora lưu trữ 6 bản sao trên 3 AZ và tối đa 15 Read Replicas Aurora replicates 6 copies across 3 AZs and supports up to 15 Read Replicas Nhớ con số vàng của Aurora: 6 bản sao dữ liệu phân bố đều trên 3 AZ. Hỗ trợ tối đa 15 Read Replicas (so với chỉ 5 của RDS thông thường) và tất cả các replica đều dùng chung 1 tầng lưu trữ phân tán. Remember the golden metrics: 6 copies across 3 AZs by default. Scales up to 15 Read Replicas (versus 5 for standard RDS), backed by unified shared storage fabric.
  • 4
    Phân biệt Web Port (80/443) vs Database Port (3306/5432) khi cấu hình Security Group Differentiate Web Ports (80/443) vs Database Ports (3306/5432) in Security Group Rules Trong đề thi SAA-C03, RDS Security Group Inbound Rule luôn cho phép đúng Database Port (MySQL 3306, Postgres 5432, MSSQL 1433, Oracle 1521...) với Source là Security Group của EC2 Web/App (sg-app). Tuyệt đối không chọn đáp án mở port 80/443 hay mở 0.0.0.0/0 cho Database. In SAA-C03 questions, RDS Security Group Inbound rules strictly allow the Database Port (MySQL 3306, Postgres 5432, MSSQL 1433, Oracle 1521...) with Source set to the EC2 Security Group ID (sg-app). Never choose answers opening port 80/443 or 0.0.0.0/0 to database tiers.
  • !
    Không bao giờ lưu Session ID trong bộ nhớ máy chủ EC2 đơn lẻ Never store Session State in ephemeral EC2 local memory Để kiến trúc máy chủ web trở thành Stateless giúp Auto Scaling Group hoạt động mượt mà, nguyên tắc kiến trúc bất biến là luôn đẩy Session State ra một lớp lưu trữ dùng chung ngoài máy chủ: Amazon ElastiCache for Redis hoặc Amazon DynamoDB. To ensure web tiers remain completely stateless for frictionless Auto Scaling, canonical best practice mandates offloading session state to Amazon ElastiCache for Redis or Amazon DynamoDB.
