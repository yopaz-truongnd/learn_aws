📬 1. Amazon SQS 📬 1. Amazon SQS
Là gì? (Definition) What is it?

Hàng đợi tin nhắn phân tán hoàn toàn được quản lý (Fully Managed Distributed Message Queue). Hoạt động theo mô hình Pull-based: Producer gửi tin vào queue, Consumer chủ động pull tin về xử lý rồi gọi lệnh xóa tin (Delete).

Fully managed distributed message queue operating on a Pull-based model: Producers push messages to queue, Consumers poll messages, process them, and explicitly delete them.

Dùng khi nào? (When to use) When to use?

Khi cần tách rời (decouple) hai tầng ứng dụng (ví dụ Web Tier và Worker Tier), lưu đệm yêu cầu khi lưu lượng truy cập tăng vọt, chống quá tải cơ sở dữ liệu hoặc xử lý tác vụ tốn thời gian ở hậu cảnh.

Decoupling application layers (e.g. Web Tier from Worker Tier), absorbing unpredictable traffic spikes (buffering), protecting backends, and offloading asynchronous heavy tasks.

Khác gì? (Key Differences) Key Differences

• Standard Queue: Throughput vô hạn, phân phối ít nhất 1 lần (at-least-once delivery), thứ tự có thể xáo trộn.
• FIFO Queue: Đúng thứ tự nghiêm ngặt (First-In-First-Out), phân phối chính xác 1 lần (exactly-once), throughput 300–3.000 msg/s.

• Standard Queue: Unlimited throughput, at-least-once delivery, best-effort ordering.
• FIFO Queue: Strict ordering (FIFO), exactly-once processing, 300–3,000 msgs/s (up to 30,000 with high-throughput mode).

Bẫy thi & Từ khóa (Traps & Keywords) Traps & Keywords

⚠️ Bẫy đề thi: Consumer xử lý xong mà không gọi DeleteMessage → Tin nhắn sẽ xuất hiện trở lại trong queue sau khi hết Visibility Timeout! Luôn bật Long Polling (1–20s) để giảm chi phí API rỗng.

⚠️ Exam Trap: Forgetting to invoke DeleteMessage post-processing causes message to reappear once Visibility Timeout expires! Always enable Long Polling (1–20s) to minimize empty poll costs.

📢 2. Amazon SNS 📢 2. Amazon SNS
Là gì? (Definition) What is it?

Dịch vụ gửi thông báo theo mô hình Publish/Subscribe (Pub/Sub) hoàn toàn được quản lý. Hoạt động theo cơ chế Push-based: Một Producer gửi tin vào Topic, hệ thống tự động đẩy tin đồng thời tới hàng ngàn Subscriber.

Fully managed Publish/Subscribe (Pub/Sub) notification service. Operates on a Push-based model: A single Producer publishes to a Topic, immediately fanning out to thousands of Subscribers.

Dùng khi nào? (When to use) When to use?

Khi một sự kiện xảy ra cần kích hoạt đồng thời nhiều hành động khác nhau (mô hình Fan-out), hoặc gửi thông báo trực tiếp cho người dùng qua SMS, Email thoại, thông báo di động (Mobile Push).

Triggering multiple downstream systems concurrently upon a single event (Fan-out pattern), or sending direct end-user notifications via SMS, Email, and Mobile Push.

Khác gì? (Key Differences) Key Differences

SNS không lưu trữ tin nhắn (không có persistence/buffer). Nếu Subscriber offline và không hỗ trợ retry → tin nhắn bị mất. Muốn lưu trữ an toàn phải kết hợp SNS + SQS Fan-out.

SNS has no built-in message persistence buffer. If a subscriber is down without delivery retry → message is lost. Combine SNS + SQS Fan-out for durable asynchronous processing.

Bẫy thi & Từ khóa (Traps & Keywords) Traps & Keywords

⚠️ Bẫy đề thi: Muốn một hàng đợi chỉ nhận một số loại tin nhắn nhất định từ SNS Topic → Sử dụng SNS Message Filtering Policy (lọc ở phía SNS), không lọc thủ công ở code ứng dụng.

⚠️ Exam Trap: To restrict a queue from receiving irrelevant messages from an SNS Topic → Apply SNS Message Filtering Policies (server-side filter), avoiding custom code filtering.

🌊 3. Amazon Kinesis 🌊 3. Amazon Kinesis
Là gì? (Definition) What is it?

Nền tảng xử lý dữ liệu luồng phân tán thời gian thực (Real-time Streaming Platform) quy mô lớn. Hoạt động dựa trên khái niệm Shards (phân mảnh dữ liệu) và duy trì bản ghi theo thứ tự thời gian.

Distributed platform for collecting, processing, and analyzing real-time streaming data at massive scale. Built on Shards with sequential, time-ordered record retention.

Dùng khi nào? (When to use) When to use?

Khi cần thu thập hàng trăm nghìn sự kiện/giây từ thiết bị IoT, log truy cập máy chủ, nhật ký giao dịch thương mại điện tử, số liệu tài chính thời gian thực để phân tích ngay lập tức hoặc phát hiện gian lận.

Ingesting hundreds of thousands of events/sec from IoT telemetry, server logs, real-time e-commerce clickstreams, and financial tickers for sub-second processing or fraud detection.

Khác gì? (Key Differences) Key Differences

• Data Streams: Real-time (70ms), người dùng tự quản lý Shard và viết consumer, dữ liệu giữ 1–365 ngày.
• Data Firehose: Near real-time (60s buffer), Serverless, tự động nạp thẳng vào S3, Redshift, OpenSearch, Splunk.

• Data Streams: Real-time (70ms), manual shard scaling, custom consumers, 1–365 day retention.
• Data Firehose: Near real-time (60s buffer), fully serverless auto-loader into S3, Redshift, OpenSearch, Splunk.

Bẫy thi & Từ khóa (Traps & Keywords) Traps & Keywords

⚠️ Bẫy đề thi: Khi nhiều ứng dụng consumer cần đọc cùng một luồng dữ liệu với độ trễ thấp độc lập nhau → Dùng Kinesis (cho phép nhiều consumer đọc đi đọc lại bản ghi), SQS thì tin nhắn bị xóa sau khi 1 consumer đọc!

⚠️ Exam Trap: When multiple independent applications must replay and consume the exact same streaming dataset concurrently → Choose Kinesis. In SQS, message vanishes once consumed!

💡 Vì sao đề thi SAA-C03 luôn chuộng mô hình này? 💡 Why is this pattern an SAA-C03 Favorite?

• Hoàn toàn tách rời (Loose Coupling): Order Service chỉ cần bắn 1 bản tin vào SNS mà không cần biết có bao nhiêu dịch vụ hạ nguồn đang lắng nghe.
• Bền vững & Không mất tin: Nếu một Worker của dịch vụ tồn kho (Inventory) bị crash hoặc bảo trì, tin nhắn vẫn được lưu an toàn trong SQS Queue 2 tới 14 ngày.
• Co giãn độc lập (Independent Scaling): Mỗi nhóm Worker tự động co giãn theo số lượng tin nhắn trong hàng đợi riêng của mình mà không ảnh hưởng lẫn nhau.
• Lọc tin nhắn bằng SNS Filter Policy: Nếu dịch vụ Fraud chỉ cần đơn hàng > $1000, gắn JSON filter trực tiếp vào SQS Subscription mà không tốn tài nguyên lọc ở code.

• Loose Coupling: The publisher sends once to SNS with zero awareness of downstream subscriber counts or destinations.
• Durability & Fault Tolerance: If Inventory workers crash, messages remain buffered safely in SQS Queue 2 for up to 14 days.
• Independent Scaling: Each downstream tier scales independently via CloudWatch metrics (Queue Depth / `ApproximateNumberOfMessagesVisible`).
• Server-side Filtering: Apply SNS Subscription Filter Policies so specific queues only receive events matching criteria (e.g. `order_amount > 1000`).

⏱️ 1. Visibility Timeout & API ChangeMessageVisibility ⏱️ 1. Visibility Timeout & ChangeMessageVisibility API

Khi một Consumer đọc tin nhắn từ SQS, tin nhắn không bị xóa ngay mà trở nên "vô hình" (invisible) đối với các Consumer khác trong một khoảng thời gian gọi là Visibility Timeout (mặc định 30s, tối đa 12h).
• Nếu Consumer xử lý xong: Gọi DeleteMessage để xóa hẳn.
• Nếu Consumer bị sập hoặc xử lý thất bại: Hết thời gian timeout, tin nhắn lại hiện ra để Consumer khác nhận và thử lại.
• Bẫy đề thi: Nếu tác vụ cần 2 phút để xử lý nhưng timeout chỉ có 30s → Tin nhắn sẽ bị đọc lặp lại! Giải pháp: Consumer phải chủ động gọi API ChangeMessageVisibility để kéo dài thời gian trước khi hết hạn.

When a consumer polls a message, it is not deleted; it becomes invisible to other consumers for the duration of the Visibility Timeout (default 30s, max 12 hours).
• If processing succeeds: Consumer calls DeleteMessage.
• If consumer crashes: Timeout expires and message becomes visible again for another worker.
• Exam Trap: If processing takes 2 minutes while timeout is 30s → Message gets processed multiple times! Remedy: Consumer must call ChangeMessageVisibility to extend timeout dynamically.

☠️ 2. Dead Letter Queue (DLQ) & Redrive Policy ☠️ 2. Dead Letter Queue (DLQ) & Redrive Policy

Nếu một tin nhắn bị lỗi cú pháp ("Poison Pill") khiến Consumer nào đọc cũng bị crash → Tin nhắn sẽ quay lại hàng đợi vô tận. Thiết lập Redrive Policy với ngưỡng maxReceiveCount (ví dụ: 5 lần). Nếu bị đọc quá 5 lần mà không xóa thành công → Tự động đẩy sang Dead Letter Queue (DLQ) để kỹ sư điều tra, không làm tắc nghẽn hàng đợi chính.

If a corrupted message ("poison pill") crashes workers repeatedly → it loops indefinitely. Configure a Redrive Policy with a maxReceiveCount threshold (e.g. 5). Once exceeded, message routes automatically to a Dead Letter Queue (DLQ) for offline diagnosis without stalling the queue.

⏳ 3. Long Polling (WaitTimeSeconds: 1 → 20s) ⏳ 3. Long Polling (WaitTimeSeconds: 1 → 20s)

• Short Polling: Consumer gọi API và SQS trả về ngay lập tức, kể cả khi hàng đợi rỗng. Tốn rất nhiều tiền gọi API rỗng và tăng độ trễ.
• Long Polling: Consumer giữ kết nối mở và chờ tối đa 20 giây (WaitTimeSeconds: 20). Ngay khi có tin nhắn mới vào queue, SQS trả về ngay.
👉 Nguyên tắc vàng: Luôn cấu hình Long Polling để giảm chi phí gọi API SQS xuống mức thấp nhất và giảm thiểu độ trễ nhận tin.

• Short Polling: API returns immediately even if queue is empty, resulting in massive empty response charges and latency spikes.
• Long Polling: Consumer waits up to 20 seconds (WaitTimeSeconds: 20) for messages to arrive.
👉 Golden Rule: Always configure Long Polling to radically reduce SQS API costs and minimize message processing latency.

🔢 4. SQS FIFO: Message Group ID & Deduplication ID 🔢 4. SQS FIFO: Message Group ID & Deduplication ID

• Message Group ID: Các tin nhắn có cùng Group ID sẽ được đảm bảo xử lý nghiêm ngặt theo đúng thứ tự. Cho phép nhiều worker xử lý song song các Group khác nhau.
• Message Deduplication ID: Ngăn chặn gửi trùng tin trong cửa sổ 5 phút. Có thể tạo thủ công bằng chuỗi băm (SHA-256) hoặc bật tính năng Content-Based Deduplication.

• Message Group ID: Messages sharing the same Group ID are processed strictly sequentially. Allows parallel workers across distinct groups.
• Message Deduplication ID: Eliminates duplicate sends within a 5-minute window. Managed via SHA-256 hashes or Content-Based Deduplication.

6. Nguyên tắc vàng ra quyết định kiến trúc — SAA-C03 6. Golden Architectural Decision Rules — SAA-C03
Các quy tắc bất biến giúp chọn đúng dịch vụ tích hợp ứng dụng trong 30 giây Inviolable rules to identify the correct integration & messaging architecture in 30 seconds
1
1 Publisher → Nhiều Consumers = SNS Topic + SQS Queues 1 Publisher → Multiple Consumers = SNS Topic + SQS Queues
Nếu đề bài yêu cầu "khi có đơn hàng mới, gửi thông báo cho nhóm vận chuyển, nhóm hóa đơn và gửi SMS cho khách hàng đồng thời mà không nghẽn" → Chọn mô hình Fan-out: SNS Topic đẩy vào nhiều SQS Queues.
When an event requires simultaneous delivery to shipping, billing, and SMS notification without blocking → Choose Fan-out: SNS Topic pushing to multiple SQS Queues.
2
Thứ tự nghiêm ngặt (Strict Order) = SQS FIFO hoặc Kinesis Strict Ordering Requirement = SQS FIFO or Kinesis Data Streams
SQS Standard và SNS Standard không đảm bảo thứ tự 100%. Nếu đề thi có từ khóa "strictly ordered", "first-in-first-out", "no duplicate processing" → Chỉ chọn SQS FIFO (tên có đuôi .fifo) hoặc Kinesis Data Streams (thứ tự giữ theo Shard).
SQS Standard and SNS Standard offer best-effort ordering only. If scenario specifies "strictly ordered", "first-in-first-out", or "exactly-once" → Must choose SQS FIFO (with .fifo suffix) or Kinesis.
3
Nạp thẳng S3/Redshift không viết code = Kinesis Data Firehose Serverless Loading into S3/Redshift without Code = Kinesis Data Firehose
Khi cần chuyển dữ liệu luồng vào S3, Redshift hay OpenSearch mà không muốn tự quản lý máy chủ hay viết mã Consumer → Luôn chọn Kinesis Data Firehose. Không bao giờ tự viết EC2 consumer nếu Firehose hỗ trợ đích đến đó.
When ingesting streams directly into S3, Redshift, or OpenSearch without managing consumer code or instances → Always choose Kinesis Data Firehose. Never manage custom EC2 consumers when Firehose supports native delivery.
4
Di chuyển giao thức cũ không sửa code = Amazon MQ Legacy Enterprise Messaging Protocol Migration = Amazon MQ
SQS và SNS sử dụng API độc quyền của AWS. Nếu đề bài nhắc đến việc di chuyển từ on-premises lên cloud mà ứng dụng sử dụng giao thức chuẩn MQTT, AMQP, STOMP, JMS (ActiveMQ / RabbitMQ) mà không được sửa code → Luôn chọn Amazon MQ.
SQS and SNS use proprietary AWS APIs. If a migration prompt mentions industry protocols like MQTT, AMQP, STOMP, JMS (ActiveMQ / RabbitMQ) with zero code rewrite → Always choose Amazon MQ.
