👤 1. AWS IAM (Identity & Access Management) 👤 1. AWS IAM (Identity & Access Management)
🔵 Là gì (1 câu) 🔵 What is it (1 sentence) Dịch vụ toàn cầu (Global Service) quản lý danh tính người dùng và kiểm soát phân quyền truy cập an toàn vào các tài nguyên AWS. A Global Service that manages user identities and securely controls permissions to AWS resources.
🟢 Dùng khi nào (Use Case điển hình) 🟢 When to use (Canonical Use Cases)
  • Cấp quyền theo nguyên tắc đặc quyền tối thiểu (Least Privilege) cho Users/Groups.
  • Cho phép dịch vụ AWS (EC2, Lambda, ECS) gọi dịch vụ khác (S3, DynamoDB) mà không lưu Access Keys trong code bằng IAM Roles.
  • Kiểm toán bảo mật định kỳ bằng Credentials Report (toàn account) và Access Advisor (từng user).
  • Grant least privilege permissions to IAM Users and Groups.
  • Allow AWS compute (EC2, Lambda, ECS) to securely call other services without embedding static credentials using IAM Roles.
  • Audit security compliance using Credentials Report (account-wide) and Access Advisor (per entity).

🔴 Điểm hay bị hỏi (Giới hạn, Mặc định, Từ khóa) 🔴 Exam Hotspots (Limits, Defaults, Keywords)
  • Mặc định: Mọi thao tác là Implicit Deny trừ khi có Allow; một Explicit Deny luôn phủ quyết mọi Allow.
  • Giới hạn: IAM Groups chỉ chứa Users, không thể lồng Group trong Group (No nested groups).

"simultaneous sign-in up to 5 accounts" → Multi-session support
  • Defaults: All actions default to Implicit Deny; an Explicit Deny always overrides any Allow.
  • Limits: IAM Groups only contain Users, cannot contain nested groups.

"without hardcoding credentials" → IAM Role
"least operational overhead / rotate keys" → IAM Role

💻 2. AWS CLI, AWS SDK & AWS CloudShell 💻 2. AWS CLI, AWS SDK & AWS CloudShell
🔵 Là gì (1 câu) 🔵 What is it (1 sentence) Bộ công cụ dòng lệnh (AWS CLI), thư viện lập trình (AWS SDK) và terminal trực tiếp trên trình duyệt (AWS CloudShell) giúp quản trị và gọi API của AWS. Command-line tools (AWS CLI), programming libraries (AWS SDK), and web terminal (AWS CloudShell) to manage and invoke AWS APIs.

  • Automate cloud infrastructure provisioning and management via scripts (AWS CLI).
  • Programmatically interact with AWS services inside application source code (AWS SDK).
  • Run commands inside browser without installing tooling or configuring access keys (AWS CloudShell).

2. Các loại Chính sách (IAM Policies) 2. IAM Policy Types
Tài liệu JSON định nghĩa: ai được phép làm gì trên tài nguyên nào JSON document: who is allowed to perform what actions on which resources
Identity-based (Gán vào User/Group/Role)
AWS Managed Policy AWS tạo và bảo trì sẵn (ví dụ AdministratorAccess). Không sửa được nội dung. Maintained by AWS (e.g. AdministratorAccess). Read-only.
Customer Managed Policy Do người dùng tự viết, có quản lý phiên bản (versioning), tái sử dụng cho nhiều thực thể. Custom defined with versioning, reusable across entities.
Inline Policy Nhúng trực tiếp 1:1 vào User hoặc Role cụ thể. Xóa User = xóa luôn Policy. Embedded 1:1 into specific User/Role. Deleted when entity is deleted.
Resource-based (Gán trực tiếp vào Tài nguyên)
S3 Bucket Policy Kiểm soát truy cập toàn bộ Bucket, hỗ trợ phân quyền Cross-Account trực tiếp. Controls access to entire bucket, enables direct cross-account access.
KMS Key Policy Bắt buộc phải có: Mọi truy cập vào KMS Key đều phải qua Key Policy. Mandatory: All access to KMS Keys must go through Key Policy.
SQS / SNS / Secrets Manager Cho phép dịch vụ hoặc tài khoản khác gửi tin/đọc secret trực tiếp. Authorizes cross-service or cross-account operations directly.

Cơ chế hoạt động How it Works User ở Account A gọi sts:AssumeRole để nhận credentials tạm thời của Role ở Account B. User in Account A calls sts:AssumeRole to receive temporary STS credentials for a Role in Account B. Gán chính sách trực tiếp lên tài nguyên ở Account B, liệt kê User/Role của Account A vào mục Principal. Policy attached directly to resource in Account B, explicitly listing Account A's User/Role as the Principal.
Danh tính & Quyền gốc Identity & Original Permissions Từ bỏ quyền gốc: Khi chuyển vai (Assume Role), User tạm thời mất toàn bộ quyền ở Account A và chỉ mang quyền của Role ở Account B. Relinquishes original permissions: When assuming a Role, the user temporarily gives up all Account A rights. Giữ nguyên quyền gốc: User vẫn giữ nguyên danh tính và toàn bộ quyền ở Account A, đồng thời đọc/ghi được tài nguyên ở Account B. Retains original identity: User keeps all Account A rights while simultaneously accessing Account B resource.

2. Permissions Policy ở Account B.
3. Policy ở Account A cho phép gọi sts:AssumeRole. 1. Trust Policy in Account B.

When performing operations across multiple services without resource policy support (e.g. managing EC2, RDS) in Account B. Khi cần copy file từ S3 Account A sang S3 Account B trong cùng một lệnh mà không muốn từ bỏ quyền ở Account A! 4 Condition Keys hay gặp nhất Top 4 Exam Condition Keys
aws:PrincipalOrgID Chỉ cho phép request đến từ các tài khoản thành viên trong AWS Organization của công ty. Thêm account mới không cần sửa policy! Restricts access to member accounts within the specified AWS Organization. Auto-applies to new accounts!
aws:SourceIP Chỉ cho phép gọi API từ dải IP tĩnh văn phòng công ty. Bẫy thi: Không dùng được nếu dịch vụ AWS gọi trung gian thay mặt user! Restricts API calls to corporate IP CIDR. Exam Trap: Fails if another AWS service calls on user's behalf!
aws:RequestedRegion Giới hạn các Region được phép khởi tạo tài nguyên (ví dụ chỉ cho ap-southeast-1), ngăn chặn việc mở server trái phép ở các vùng khác. Restricts approved regions for creating resources (e.g. only ap-southeast-1), preventing rogue deployments.
aws:MultiFactorAuthPresent Bắt buộc phải đăng nhập bằng thiết bị MFA thì mới được thực thi hành động nhạy cảm (như DeleteBucket, TerminateInstances). Mandates active MFA authentication before executing high-risk actions (e.g. DeleteBucket, TerminateInstances).
Bộ 3 công cụ Audit & Phân tích IAM IAM Audit & Analysis Trio
IAM Credential Report (Cấp độ Account) Tải về file CSV tổng hợp toàn bộ thông tin đăng nhập của mọi IAM User trong tài khoản: mật khẩu tạo khi nào, có bật MFA không, Access Key xoay vòng bao lâu. Downloads an account-wide CSV file listing all IAM users, password creation dates, MFA status, and Access Key rotation age.
IAM Access Advisor (Cấp độ Entity) Hiển thị trực tiếp trên Console thời điểm lần cuối cùng một User/Role sử dụng từng dịch vụ AWS. Dùng để thu hồi bớt quyền không dùng theo nguyên tắc Least Privilege. Console view of service last-accessed timestamps for a User/Role. Used to prune unused permissions for Least Privilege.
IAM Access Analyzer (Phát hiện rò rỉ) Dùng suy luận tự động (Automated Reasoning) quét toàn bộ S3, KMS, SQS, IAM Role để cảnh báo tài nguyên nào đang bị chia sẻ ra ngoài Account hoặc để chế độ Public! Leverages automated reasoning to scan S3, KMS, SQS, and IAM Roles, alerting on resources shared externally or made public!

Permissions Boundary (Ranh giới phân quyền) Permissions Boundary
Dùng cho bài toán: "Cho phép lập trình viên tự tạo IAM Role cho ứng dụng của họ mà không sợ họ tự cấp quyền Admin cho chính mình?"
👉 Đáp án: Bắt buộc lập trình viên phải gắn Permissions Boundary khi tạo Role. Quyền thực tế của Role là phần giao (Intersection) giữa Identity Policy và Permissions Boundary.
Solves the classic exam dilemma: "Allow developers to create IAM Roles without escalating privileges to AdministratorAccess?"
👉 Answer: Enforce a Permissions Boundary on role creation. Effective permissions are strictly the intersection between Identity Policy and Permissions Boundary.
Service Control Policies (SCP) Service Control Policies (SCPs)
Áp dụng ở cấp Root hoặc OU trong AWS Organizations. SCP KHÔNG BAO GIỜ cấp quyền, chỉ đặt trần quyền tối đa (Guardrail). SCP không áp dụng cho tài khoản Management (Master Account). Explicit Deny ở SCP sẽ vô hiệu hóa mọi quyền của cả Root User ở account con!
Applied at Root or OU levels in AWS Organizations. SCPs never grant permissions, only define guardrail boundaries. SCPs do not restrict the Management Account. An Explicit Deny in an SCP overrides even the Root User of member accounts!
IAM Identity Center (AWS SSO)
Giải pháp đăng nhập một lần (Single Sign-On) tập trung cho hàng trăm tài khoản AWS trong Organizations. Tích hợp trực tiếp với Active Directory, Okta, Google Workspace, thay thế hoàn toàn việc tạo IAM Users rải rác.
Centralized Single Sign-On (SSO) across hundreds of AWS accounts in Organizations. Directly integrates with Active Directory, Okta, Google Workspace, eliminating sprawling IAM Users.
Cùng Account vs Khác Account Same Account vs Cross-Account Rules
• Cùng 1 Account: Chỉ cần có Allow ở 1 bên (Identity Policy HOẶC Resource Policy) là truy cập được.
• Khác Account: BẮT BUỘC phải có Allow ở CẢ HAI PHÍA (Identity Policy cấp phép đi ra VÀ Resource Policy / Role Trust cho phép đi vào).
• Same Account: Allow on ONE side (Identity Policy OR Resource Policy) is sufficient.
• Cross-Account: Allow is MANDATORY on BOTH sides (Identity Policy permits outbound AND Resource Policy / Trust allows inbound).

    Nguyên tắc đặc quyền tối thiểu (Least Privilege) Principle of Least Privilege Chỉ cấp đúng và đủ quyền cần thiết để hoàn thành công việc. Luôn bắt đầu từ quyền tối thiểu và mở rộng dần dựa trên báo cáo của IAM Access Advisor. Grant only the minimum permissions necessary to perform the specified job. Begin with restrictive access and prune unused permissions via IAM Access Advisor.
  • 2
    EC2 Instance Profiles: dùng IAM Role, không nhúng Access Key EC2 Instance Profiles: Use IAM Roles, Never Hardcode Access Keys Luôn gán IAM Role cho EC2 / Lambda để máy chủ tự động nhận credentials ngắn hạn qua STS, tuyệt đối không lưu file cấu hình có chứa Access Key ID / Secret Key trên đĩa. Always attach IAM Roles to EC2 / Lambda instances so they receive short-term STS credentials automatically. Never store static access keys in code or on disk.
  • 3
    Cross-Account: IAM Role + STS AssumeRole Cross-Account: IAM Role + STS AssumeRole Ủy quyền truy cập giữa các tài khoản AWS thông qua việc đóng vai IAM Role (AssumeRole) thay vì tạo tài khoản người dùng trùng lặp ở tài khoản mục tiêu. Federate cross-account access by assuming IAM Roles via STS rather than maintaining duplicate IAM Users across different accounts.
  • !
    Explicit Deny luôn chiến thắng tất cả Explicit Deny Always Wins Dù có bao nhiêu câu lệnh Allow, chỉ cần xuất hiện duy nhất 1 Explicit Deny ở bất kỳ tầng nào (SCP, Boundary, Identity, Resource) là toàn bộ request bị chặn ngay lập tức. No matter how many Allow statements exist, a single Explicit Deny anywhere (SCP, Boundary, Identity, Resource) immediately and permanently rejects the request.
