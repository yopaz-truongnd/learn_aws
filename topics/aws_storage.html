1. Tam giác lưu trữ EC2: EBS vs EFS vs Instance Store 1. The EC2 Storage Triad: EBS vs EFS vs Instance Store
Ba mô hình lưu trữ với đặc tính kiến trúc, phạm vi mạng và vòng đời hoàn toàn khác biệt Three distinct storage architectures with unique network scope and lifecycles
Amazon EBS (Elastic Block Store)
Ổ đĩa khối qua mạng (Network Block Device). Khóa chặt trong 1 Availability Zone (AZ). Vòng đời độc lập với EC2 instance. Cho phép snapshot lên S3, mở rộng dung lượng và thay đổi loại đĩa realtime không downtime (Elastic Volumes).
Network BlockAZ-LockedHĐH Boot & Database
Network-attached block device locked to a single AZ. Persists independently of instance lifecycle. Supports S3 snapshots, on-the-fly volume resizing, and type changes without downtime.
Network BlockAZ-LockedOS Boot & Databases
Amazon EFS (Elastic File System)
Hệ thống tệp mạng dùng chung (Shared NFSv4.1), chuẩn POSIX filesystem. Tự động co giãn (Elastic), phân tán đa vùng khả dụng (Multi-AZ). Hàng trăm máy chủ EC2, container ECS/Fargate và Lambda có thể đọc/ghi đồng thời.
Shared File (NFS)Multi-AZWeb Server Farm / CMS
Managed network filesystem (NFSv4.1) with POSIX compliance. Automatically elastic across Multi-AZ. Hundreds of EC2 instances, ECS/Fargate containers, and Lambda can read/write simultaneously.
Shared File (NFS)Multi-AZWeb Farms / CMS
EC2 Instance Store (Ephemeral Storage)
Ổ cứng SSD/NVMe vật lý gắn trực tiếp vào phần cứng máy chủ chủ (Host). IOPS cực cao (hàng triệu IOPS), độ trễ micro-second, không tốn băng thông mạng. Mất toàn bộ dữ liệu khi instance bị Stop hoặc Terminate.
Hardware AttachedTạm thời (Ephemeral)Cache / Buffer / NoSQL
Physical SSD/NVMe drives physically attached to the host hardware. Ultra-high IOPS (millions), sub-millisecond latency, zero network hops. Data is permanently lost on Stop or Terminate.
Hardware AttachedEphemeralCache / Buffers / NoSQL
Amazon S3 (So sánh đối chiếu - Object Store)
Lưu trữ đối tượng (Object Storage), không phải block hay file system. Truy xuất qua REST API / HTTP. Độ bền 11 số 9 (99.999999999%). Không thể dùng làm ổ đĩa gắn (mount) cho hệ điều hành EC2 để cài OS.
Object StorageServerless / HTTPData Lake / Static Media
Object storage, not a mountable filesystem or block device. Accessed via HTTP/REST API. 11 9s durability. Cannot be attached as a boot drive or standard OS mount.
Object StorageServerless / HTTPData Lake / Static Media

3. Vận hành EBS: Snapshots, Mã hóa & Multi-Attach 3. EBS Operations: Snapshots, Encryption & Multi-Attach
Cơ chế bảo vệ dữ liệu, sao lưu tăng trưởng (Incremental) và chia sẻ đĩa trên cùng AZ Data protection mechanisms, incremental backups, and same-AZ block sharing
📸 Cơ chế EBS Snapshots 📸 EBS Snapshot Architecture
Sao lưu tăng trưởng (Incremental Backup) Snapshot được lưu ngầm trên Amazon S3 (dù bạn không nhìn thấy trực tiếp trong S3 bucket). Lần snapshot đầu tiên sao lưu toàn bộ block đã ghi. Các lần snapshot kế tiếp chỉ sao lưu những block thay đổi (Delta). Xóa snapshot trước không làm hỏng snapshot sau. Snapshots are stored under the hood in Amazon S3. The initial snapshot copies all written blocks; subsequent snapshots only capture modified blocks (deltas). Deleting an earlier snapshot does not corrupt subsequent ones.
EBS Snapshot Archive & FSR Archive Tier: Giảm chi phí tới 75% cho các snapshot lưu trữ dài hạn (trên 90 ngày). Thời gian khôi phục mất từ 24 đến 72 giờ.
Fast Snapshot Restore (FSR): Loại bỏ hoàn toàn độ trễ khởi tạo (I/O latency) khi restore volume từ snapshot, đạt hiệu năng tối đa ngay từ giây đầu tiên. Archive Tier: Up to 75% cheaper for long-term compliance retention (>90 days). Restores take 24–72 hours.
Fast Snapshot Restore (FSR): Eliminates initialization I/O latency when instantiating new volumes from snapshots.
Chuyển đĩa sang AZ hoặc Region khác Vì EBS volume bị khóa cứng trong 1 AZ, quy trình duy nhất để chuyển sang AZ khác hoặc Region khác là: Tạo Snapshot → Copy Snapshot (sang AZ/Region đích) → Tạo Volume mới từ Snapshot. Because EBS volumes are strictly AZ-locked, the standard pattern to relocate is: Create Snapshot → Copy Snapshot (to target AZ/Region) → Create Volume from Snapshot.
🔐 Mã hóa EBS (EBS Encryption) 🔐 EBS Encryption & Security
Mã hóa toàn diện xuyên suốt (End-to-End) Tích hợp dịch vụ AWS KMS (AES-256). Khi bật mã hóa, tự động bảo vệ:
  • Dữ liệu lưu tại chỗ trên volume (Data at rest).
  • Dữ liệu truyền giữa máy chủ EC2 và ổ đĩa EBS (In-flight data).
  • Toàn bộ các bản Snapshots tạo ra từ volume đó.
  • Tất cả các Volume sinh ra từ các Snapshot mã hóa.
 Integrated with AWS KMS (AES-256). Encrypting an EBS volume automatically secures:
  • Data at rest inside the volume.
  • In-flight traffic between EC2 host and EBS storage.
  • All snapshots created from the volume.
  • All subsequent volumes restored from those snapshots.
Quy trình mã hóa một Root Volume chưa mã hóa Đề thi SAA-C03 rất hay hỏi quy trình này:
  1. Tạo Snapshot của Root Volume chưa mã hóa.
  2. Copy Snapshot đó và đánh dấu chọn cờ Encrypt (chọn KMS key).
  3. Tạo Volume mới từ bản Snapshot đã mã hóa.
  4. Gắn Volume mới vào EC2 làm Root Device (`/dev/xvda`).
 Crucial SAA-C03 exam scenario to encrypt an unencrypted root drive:
  1. Create snapshot of unencrypted root volume.
  2. Copy snapshot while enabling Encryption (choose KMS key).
  3. Create new volume from encrypted snapshot copy.
  4. Attach new encrypted volume as root device (`/dev/xvda`).

Ứng dụng bắt buộc phải dùng Cluster-aware Filesystem (như GFS2, GlusterFS) để ngăn ngừa hỏng file (Data Corruption). Dùng cho clustered apps đòi hỏi High Availability failover (e.g., Teradata). 4. Chuyên sâu Amazon EFS (Elastic File System) 4. Amazon EFS Deep Dive & Architecture
Hệ thống tệp mạng POSIX chia sẻ đa vùng Multi-AZ, tự động co giãn và quản lý vòng đời dữ liệu Multi-AZ POSIX shared network filesystem with automated tiering and lifecycle management
Kiến trúc kết nối & Mount Targets
• Hỗ trợ giao thức NFSv4.1 (chỉ dành cho máy chủ Linux, không hỗ trợ trực tiếp Windows).
• Tạo Mount Target tại mỗi AZ trong VPC. Mỗi Mount Target có IP riêng và được bảo vệ bởi Security Group (Mở cổng 2049).
• Khả năng chịu lỗi cao: Dữ liệu phân tán trên nhiều AZ (Regional Storage) bảo đảm khả năng sống sót kể cả khi mất 1 AZ.
• Tương thích hoàn toàn với EC2, Amazon ECS, AWS Fargate, AWS Lambda và on-premises qua AWS Direct Connect / VPN.
• Uses NFSv4.1 protocol (Linux POSIX compliant; not intended for Windows).
• Deploys a Mount Target in each VPC subnet/AZ with dedicated private IP secured by Security Group (Port 2049).
• High fault tolerance: Data synchronously mirrored across multiple AZs (Regional Storage).
• Fully interoperable with EC2, ECS, Fargate, Lambda, and on-premises via Direct Connect/VPN.
Các tầng lưu trữ & Lifecycle Management
• EFS Standard: Dành cho tệp truy xuất thường xuyên, độ trễ đọc/ghi tính bằng mili-giây thấp.
• EFS Infrequent Access (EFS IA): Tiết kiệm tới 92% chi phí lưu trữ. Tính thêm phí nhỏ trên mỗi GiB đọc/ghi.
• EFS Archive: Tầng lưu trữ cho dữ liệu truy xuất vài lần mỗi năm, chi phí lưu trữ cực rẻ.
• EFS Lifecycle Management: Tự động chuyển tệp sang IA sau số ngày không truy xuất (7, 14, 30, 60, 90 ngày) và chuyển ngược lại Standard khi có request đọc.
• EFS Standard: For frequently accessed active files with lowest latency.
• EFS Infrequent Access (EFS IA): Up to 92% cost savings on storage. Incurs a small retrieval charge per GiB.
• EFS Archive: Lowest cost storage for files accessed only a few times annually.
• EFS Lifecycle Management: Automatically moves idle files to IA (e.g. after 30 days) and restores them to Standard upon read.
Chế độ hiệu năng (Performance Modes)
• General Purpose (Mặc định): Tối ưu độ trễ cho từng thao tác tệp, thích hợp cho web hosting, CMS (WordPress), home directories và phần lớn ứng dụng thông thường.
• Max I/O: Mở rộng quy mô IOPS và thông lượng tổng thể cực đại cho hàng trăm máy chủ ghi dữ liệu song song (Big Data analytics, render video, xử lý khoa học). Độ trễ tệp đơn lẻ cao hơn đôi chút.
• General Purpose (Default): Latency-optimized for general web servers, WordPress CMS, and home directories.
• Max I/O: Scales to massive aggregate throughput and IOPS for hundreds of concurrent clients (Big Data, video rendering, scientific compute), with slightly higher base latency per metadata operation.
Chế độ thông lượng (Throughput Modes)
• Elastic Mode (Khuyên dùng): Tự động điều chỉnh thông lượng đọc/ghi theo thời gian thực dựa trên nhu cầu của ứng dụng, không cần dự đoán trước dung lượng.
• Provisioned Mode: Khóa cứng mức thông lượng cố định (ví dụ 1 GiB/s) bất kể dung lượng dữ liệu trong tệp là bao nhiêu (trả phí theo thông lượng đặt trước).
• Bursting Mode: Thông lượng tỷ lệ thuận theo dung lượng lưu trữ (50 KiB/s trên mỗi GiB dữ liệu) kèm cơ chế tích điểm Burst Credit.
• Elastic Mode (Recommended): Dynamically scales throughput based on real-time activity without manual management.
• Provisioned Mode: Guarantees dedicated throughput independent of stored data volume (e.g., 1024 MiB/s on a small 10 GB file).
• Bursting Mode: Throughput scales proportionally to volume size (50 KiB/s per GiB) backed by burst credits.

5. Chuyên sâu EC2 Instance Store (Lưu trữ tạm thời) 5. EC2 Instance Store Deep Dive
Ổ cứng NVMe SSD gắn vật lý trên máy chủ chủ: Tốc độ tối thượng nhưng dữ liệu tạm thời (Ephemeral) Physical host-attached NVMe SSDs: Maximum performance with ephemeral persistence rules
⚡ Hiệu năng phần cứng ⚡ Hardware Performance
Không phụ thuộc băng thông mạng Khác với EBS (truy xuất qua mạng VPC Ethernet), Instance Store được gắn trực tiếp trên khe PCIe/NVMe của máy chủ vật lý. Đạt hàng triệu IOPS với độ trễ micro-second, không bị giới hạn bởi chuẩn EBS-Optimized. Unlike EBS (accessed over VPC network fabric), Instance Store is directly plugged into physical host PCIe/NVMe slots. Delivers millions of IOPS with sub-millisecond latency.
Đã bao gồm trong chi phí Instance Không tính phí riêng biệt như EBS Volume. Các loại máy chủ có chữ 'd' trong tên (ví dụ: `c5d.4xlarge`, `m5d.large`, `i3en.metal`) tự động tích hợp sẵn ổ đĩa Instance Store. Storage is included in the base hourly rate of the EC2 instance. Identified by instances containing 'd' in their family name (e.g., `c5d`, `m5d`, `i3en`).
⚠️ Vòng đời dữ liệu (Data Lifecycle) ⚠️ Ephemeral Data Lifecycle
Trường hợp còn giữ được dữ liệu Dữ liệu trên Instance Store VẪN CÒN khi khởi động lại hệ điều hành bên trong (OS Reboot). Data on Instance Store SURVIVES soft internal operating system reboots (OS Reboot).
Trường hợp MẤT SẠCH dữ liệu Dữ liệu BỊ MẤT HOÀN TOÀN khi:
  • Người dùng thực hiện Stop Instance (do máy chuyển sang host vật lý khác).
  • Thực hiện Terminate Instance.
  • Hỏng phần cứng máy chủ chủ (Hardware failure).
 Data is PERMANENTLY LOST when:
  • Instance is Stopped (migrates to a different physical host).
  • Instance is Terminated.
  • Underlying hardware host degrades or fails.
🎯 Ứng dụng & Kiến trúc tối ưu 🎯 Ideal Architectural Patterns
Vùng đệm, Cache & Dữ liệu tạm Lý tưởng cho bộ nhớ đệm (Web/App Cache), hàng đợi đệm (Scratch buffers), không gian tráo đổi RAM (Swap space) và các file index tìm kiếm tạm thời. Ideal for local app caches, scratch buffers, memory swap space, and temporary indexing catalogs.
Hệ quản trị CSDL phân tán có cơ chế nhân bản Rất phù hợp cho các cụm NoSQL hoặc Big Data có tính năng nhân bản dữ liệu tự động giữa các node (e.g., Apache Cassandra, Hadoop HDFS, MongoDB replica sets, Elasticsearch). Mất 1 node không làm mất dữ liệu của toàn cụm. Perfect for distributed replicated clusters where the software engine handles multi-node replication (e.g. Apache Cassandra, Hadoop HDFS, Elasticsearch). Loss of one node does not compromise dataset.

7. Các bẫy & Kịch bản đề thi thường gặp (SAA-C03 Traps) 7. Common Exam Traps & Scenarios (SAA-C03)
Những điểm mấu chốt đề thi thường xuyên đưa vào đáp án gây nhiễu High-frequency exam trick points and distractor patterns
Cấu hình RAID trên ổ đĩa EBS
• RAID 0 (Striping): Gộp nhiều volume EBS để đạt thông lượng (Throughput) và IOPS tối đa khi 1 volume riêng lẻ không đáp ứng nổi. Nhược điểm: Không có khả năng chịu lỗi (Nếu 1 volume hỏng, mất toàn bộ dữ liệu).
• RAID 1 (Mirroring): Nhân bản dữ liệu đồng thời lên 2 volume để tăng tính chịu lỗi. Nhược điểm: Tốn gấp đôi dung lượng lưu trữ và nhân đôi IOPS ghi.
• RAID 5 và RAID 6: AWS KHUYẾN CÁO KHÔNG DÙNG trên EBS vì cơ chế tính toán parity làm hao tổn thông lượng I/O trầm trọng.
• RAID 0 (Striping): Combines multiple EBS volumes to maximize aggregate throughput/IOPS. Trade-off: Zero fault tolerance (one drive fails = entire array corrupted).
• RAID 1 (Mirroring): Mirrors data across two volumes for redundancy. Trade-off: 2x storage cost and double write IOPS.
• RAID 5 & 6: NOT RECOMMENDED by AWS on EBS due to parity calculation I/O penalties.
Đặc tính DeleteOnTermination
• Khi khởi tạo EC2, thuộc tính DeleteOnTermination của Root EBS Volume mặc định được đặt là TRUE (Volume sẽ tự động bị xóa sổ khi xóa máy chủ).
• Đối với các Attached EBS Volumes gắn thêm, giá trị này mặc định là FALSE (Volume vẫn tồn tại độc lập sau khi instance bị terminate).
• Trong đề thi: Nếu muốn giữ lại dữ liệu Root khi xóa máy, phải chuyển cờ này sang false trong cấu hình Block Device Mapping.
• On launch, DeleteOnTermination for the Root EBS volume defaults to TRUE (destroyed when instance terminates).
• For additional Attached Volumes, it defaults to FALSE (retained independently).
• Exam tip: To prevent accidental root data deletion on termination, explicitly set this flag to false.
gp2 vs gp3: Sự khác biệt về chi phí & cấu hình
• Đề bài yêu cầu: "Tăng thông lượng lên 500 MiB/s cho ổ đĩa 100 GiB với chi phí tối ưu nhất".
• Với gp2: Bắt buộc phải tăng dung lượng lên hàng nghìn GiB chỉ để lấy thêm IOPS/Throughput → Lãng phí ngân sách.
• Với gp3: Chọn cấu hình trực tiếp 500 MiB/s mà vẫn giữ nguyên dung lượng 100 GiB → gp3 luôn là câu trả lời đúng khi cần tối ưu chi phí!
• Scenario: "Need 500 MiB/s throughput on a 100 GiB volume with minimum cost".
• With gp2: You are forced to over-provision gigabytes just to scale baseline performance.
• With gp3: You tune throughput/IOPS independently without paying for unneeded storage → gp3 is the optimal answer!
EFS One Zone vs Regional Storage
• Mặc định EFS phân tán đa vùng (Regional - Multi-AZ).
• Để tiết kiệm 47% chi phí lưu trữ cho môi trường Development / Staging, có thể chọn EFS One Zone (lưu trữ trong 1 AZ duy nhất).
• Khi dùng EFS One Zone, AWS khuyến nghị kích hoạt tính năng AWS Backup tự động để đề phòng rủi ro mất toàn bộ AZ.
• By default, EFS is Multi-AZ Regional.
• For non-critical Dev/Test workloads, select EFS One Zone for 47% cost savings.
• Pairing EFS One Zone with AWS Backup is the canonical best practice to mitigate single-AZ failure risks.

8. Nguyên tắc vàng khi làm bài thi (SAA-C03 Golden Rules) 8. SAA-C03 Exam Golden Rules
Bộ quy tắc bất biến giúp loại trừ ngay các đáp án sai trong đề thi chứng chỉ Essential axioms to rapidly eliminate incorrect choices in the exam
  • 1
    EBS Volume bị khóa chặt trong một Availability Zone (AZ) EBS Volumes are strictly bound to a Single Availability Zone Không bao giờ có chuyện gắn trực tiếp 1 volume EBS sang máy chủ EC2 ở AZ khác. Muốn chuyển sang AZ khác, bắt buộc phải chụp Snapshot rồi tạo Volume mới ở AZ đích. You can NEVER directly attach an EBS volume to an EC2 instance in a different AZ. To cross AZs, take a Snapshot and restore a new volume in the destination AZ.
  • 2
    st1 và sc1 tuyệt đối KHÔNG thể dùng làm Boot Volume st1 and sc1 CANNOT be used as OS Boot Volumes Chỉ có các loại đĩa SSD (gp2, gp3, io1, io2) mới được phép làm ổ đĩa khởi động hệ điều hành. Bất kỳ đáp án nào đề xuất st1/sc1 làm Boot Volume đều là đáp án sai. Only SSD-backed volumes (gp2, gp3, io1, io2) are supported as boot drives. Any option suggesting st1 or sc1 as a boot volume is immediately invalid.
  • 3
    Cần hệ thống tệp chia sẻ Multi-AZ cho Linux → Luôn chọn Amazon EFS Shared Multi-AZ Filesystem for Linux → Always Pick Amazon EFS Khi đề bài nhắc đến chia sẻ tệp đồng thời giữa nhiều máy chủ Linux trải rộng trên nhiều AZ và tuân thủ POSIX, câu trả lời chuẩn xác là Amazon EFS (hoặc FSx for Windows nếu là máy chủ Windows SMB). When a question specifies concurrent POSIX file access across multiple Linux EC2 instances in different AZs, Amazon EFS is always the intended architecture.
  • !
    Instance Store mất sạch dữ liệu khi Stop hoặc Terminate Instance Store loses all data upon Instance Stop or Terminate Không bao giờ lưu trữ dữ liệu cơ sở dữ liệu vĩnh viễn trên Instance Store nếu không có cơ chế replication phân tán ở tầng ứng dụng (như Cassandra/HDFS). Khi máy chủ Stop, dữ liệu sẽ bốc hơi vĩnh viễn và không thể khôi phục! Never store permanent state on an Instance Store without application-level distributed replication (e.g. Cassandra, HDFS). Once the instance stops, data evaporates permanently!
