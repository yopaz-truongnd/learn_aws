1. Nền tảng kiến trúc: Khả năng co giãn (Scalability) vs Sẵn sàng cao (High Availability) 1. Architectural Foundations: Scalability vs High Availability
Bốn trụ cột thiết kế hệ thống chịu tải và kháng lỗi trong điện toán đám mây Four foundational pillars for building fault-tolerant and scalable cloud systems
Vertical Scalability (Scale Up / Down)
Tăng hoặc giảm kích thước phần cứng của 1 máy chủ đơn lẻ (ví dụ: đổi instance từ t3.nano lên u-12tb1.metal). Thường áp dụng cho cơ sở dữ liệu quan hệ (RDS, SQL Server). Luôn bị giới hạn bởi trần phần cứng vật lý và đòi hỏi downtime khi nâng cấp.
Scale UpTăng RAM/CPUDatabase Non-Distributed
Increasing or decreasing hardware sizing on a single compute node (e.g. changing instance from t3.nano to u-12tb1.metal). Common for relational databases (RDS, SQL Server). Limited by physical hardware boundaries and requires brief downtime.
Scale UpVertical SizingNon-Distributed DBs
Horizontal Scalability (Scale Out / In)
Thêm hoặc bớt số lượng máy chủ chạy song song theo nhu cầu tải (ví dụ: từ 2 máy chủ tăng lên 20 máy chủ EC2). Lý tưởng cho các ứng dụng Stateless Web/API. Khả năng mở rộng gần như vô hạn và không gây gián đoạn hệ thống.
Scale OutThêm máy chủStateless Web Apps / ASG
Adding or removing instances horizontally to match current demand (e.g. scaling from 2 to 20 EC2 instances). Ideal for stateless distributed web applications. Infinitely scalable with zero downtime.
Scale OutHorizontal FleetStateless Web Apps / ASG
High Availability (Tính sẵn sàng cao - HA)
Vận hành ứng dụng trên ít nhất 2 Availability Zones (Multi-AZ) để loại bỏ điểm lỗi đơn lẻ (Single Point of Failure - SPOF). Nếu 1 AZ bị sập do thiên tai, hệ thống vẫn duy trì hoạt động thông qua các máy chủ còn lại ở các AZ khác.
Multi-AZKháng lỗi (Fault-Tolerant)Không SPOF
Running identical workloads across at least two Availability Zones (Multi-AZ) to eliminate Single Points of Failure (SPOF). Ensures continuous availability even during catastrophic data center outages.
Multi-AZFault-TolerantNo SPOF
Elasticity & Agility (Độ đàn hồi & Linh hoạt)
Elasticity: Hệ thống tự động co giãn chính xác theo tải thực tế (Auto Scaling), tự tăng khi đông khách và giảm khi vắng khách để tối ưu chi phí.
Agility: Khả năng cấp phát nhanh tài nguyên công nghệ chỉ trong vài giây thay vì chờ hàng tháng mua máy chủ vật lý.
Đàn hồi tự độngPay-as-you-goChi phí tối ưu
Elasticity: Dynamic self-adjusting capacity that mirrors real-time load patterns, pruning resources when idle to prevent waste.
Agility: Rapid automated provisioning within seconds rather than months of manual datacenter procurement.

Cross-Zone Balancing, SSL/TLS Termination, SNI, Sticky Sessions và Connection Draining Cross-Zone Balancing, SSL/TLS Termination, SNI, Sticky Sessions, and Connection Draining
🌐 Cross-Zone Load Balancing 🌐 Cross-Zone Balancing
Phân phối lưu lượng đồng đều giữa các AZ Khi bật tính năng này, mỗi node của Load Balancer sẽ phân phối lưu lượng đồng đều tới tất cả target trong tất cả AZ, tránh tình trạng AZ có nhiều máy chủ thì nhàn rỗi còn AZ ít máy chủ thì quá tải. Distributes traffic evenly across all registered instances in all enabled AZs, preventing unbalanced loads when instance distribution is skewed across zones.
Sự khác biệt về cấu hình & chi phí • ALB: Mặc định BẬT (Enabled), miễn phí truyền dữ liệu giữa các AZ (No data transfer charges).
• NLB: Mặc định TẮT (Disabled). Nếu bật, bạn phải trả phí Data Transfer liên AZ (Inter-AZ Data Transfer Cost). • ALB: Always ENABLED by default at no extra data transfer fee.
• NLB: DISABLED by default. If enabled, inter-AZ data transfer fees apply.
🔒 SSL Certificates & SNI 🔒 SSL/TLS & SNI
Server Name Indication (SNI) Cho phép client gửi tên miền mục tiêu (`Host: api.example.com`) ngay trong gói bắt tay TLS đầu tiên. Giúp Load Balancer có thể tải nhiều chứng chỉ SSL khác nhau trên cùng 1 Listener duy nhất.
ALB & NLB hỗ trợMulti-domain SSL Enables clients to indicate hostname during initial TLS handshake. Allows one single listener on ALB/NLB to host multiple distinct SSL certificates for different subdomains.
Supported on ALB & NLBMulti-domain SSL
SSL Termination tại tầng ELB Load Balancer giải mã SSL (Decrypt) bằng chứng chỉ quản lý bởi AWS Certificate Manager (ACM), sau đó chuyển tiếp traffic HTTP thuần vào target trong Private Subnet → Giảm tải CPU cho các máy chủ EC2 backend. ELB offloads SSL decryption using ACM certificates, passing unencrypted HTTP into private subnets → Frees backend EC2 CPU cycles.
🍪 Sticky Sessions & Draining 🍪 Sticky Sessions & Draining
Sticky Sessions (Session Affinity) Bắt buộc các request từ 1 người dùng cụ thể luôn luôn được chuyển hướng đến cùng một EC2 instance backend duy nhất. Hỗ trợ thông qua Duration-based Cookie (do ALB sinh) hoặc Application Cookie (do app sinh). Nhược điểm: Có thể gây mất cân bằng tải giữa các máy chủ. Pins user requests to the exact same backend instance via cookies. Supported via ALB duration-based or application-based cookies. Tradeoff: Potential workload imbalance.
Connection Draining (Deregistration Delay) Khi 1 instance chuyển sang trạng thái Unhealthy hoặc đang bị ASG Terminate, ELB sẽ ngừng gửi request mới, nhưng cho phép các kết nối đang dang dở (in-flight requests) hoàn thành trong khoảng thời gian cấu hình (mặc định 300 giây, phạm vi từ 1 đến 3600 giây). Allows existing in-flight requests to gracefully complete when an instance is deregistering or unhealthy (default 300s, configurable from 1 to 3600s).

4. Chuyên sâu Auto Scaling Groups (ASG) 4. Auto Scaling Groups (ASG) Deep Dive
Kiến trúc co giãn tự động theo tải, cơ chế kiểm tra sức khỏe và chiến lược mở rộng Elastic workload scaling, health checks, and lifecycle management
Launch Templates vs Launch Configurations
• Launch Template (Khuyên dùng): Bản thiết kế chuẩn định nghĩa: AMI ID, Instance Type, Key Pair, Security Groups, IAM Role, User Data script. Hỗ trợ quản lý phiên bản (Versioning), cho phép cấu hình kết hợp On-Demand và Spot Instances, kế thừa tham số.
• Launch Configuration (Thế hệ cũ): Đã bị AWS coi là Legacy. Không có phiên bản, muốn sửa phải tạo bản mới từ đầu. Đề thi luôn yêu cầu chuyển sang Launch Template.
• Launch Template (Recommended): The canonical specification defining AMI ID, Instance Type, Key Pair, Security Groups, IAM Roles, User Data. Supports versioning and mixing On-Demand with Spot instances.
• Launch Configuration (Legacy): Deprecated legacy mechanism without versioning support.
Thông số Capacity (Min, Desired, Max)
• Minimum Size: Số lượng máy chủ tối thiểu luôn phải duy trì (kể cả khi không có khách truy cập).
• Desired Capacity: Số lượng máy chủ hiện tại đang vận hành. ASG luôn cố gắng duy trì số máy đúng bằng con số này.
• Maximum Size: Trần số lượng máy chủ tối đa được phép sinh ra khi có đột biến tải, giúp chặn nguy cơ bùng nổ chi phí ngoài kiểm soát.
• Minimum Size: Baseline instances that must always be running.
• Desired Capacity: Current target count of instances. ASG self-heals towards this value.
• Maximum Size: Ceiling cap on instance scaling to prevent runaway budget spikes.
Cơ chế kiểm tra sức khỏe (ASG Health Checks)
• EC2 Status Checks (Mặc định): ASG chỉ kiểm tra máy chủ có chạy không qua tình trạng phần cứng máy chủ AWS (System status check và Instance status check).
• ELB Health Checks: Nếu máy chủ vẫn chạy nhưng Web App bên trong bị crash (trả về lỗi HTTP 500 hoặc rớt ping `/healthz`), Target Group sẽ đánh dấu Unhealthy. Khi cấu hình Health Check Type = ELB, ASG sẽ tự động hủy diệt (Terminate) máy chủ lỗi và khởi tạo máy chủ mới thay thế!
• EC2 Status Checks (Default): Monitors raw hardware hypervisor availability.
• ELB Health Checks: If the web service crashes (e.g. returning 500s or failing `/healthz`), the Target Group flags it unhealthy. Under ELB Health Check mode, ASG automatically terminates and replaces the degraded instance!
Quy tắc chọn máy chủ khi Terminate (Default Policy)
Thứ tự ưu tiên khi ASG cần giảm bớt máy chủ (Scale In):
  1. Chọn AZ có nhiều instance nhất.
  2. Trong AZ đó, chọn máy chủ dùng Launch Template phiên bản cũ nhất.
  3. Chọn máy chủ có thời gian chạy gần mốc tính phí 1 giờ kế tiếp nhất.
  4. Nếu vẫn trùng, chọn ngẫu nhiên.
Default termination precedence during Scale In:
  1. Identifies the AZ with the most instances.
  2. Selects instances with the oldest Launch Template version.
  3. Selects instance closest to the next billing hour.
  4. Random tie-breaker.

5. Phân loại 4 chính sách co giãn Auto Scaling (Scaling Policies) 5. ASG Dynamic Scaling Policies
Chiến lược kích hoạt tăng/giảm quy mô tự động theo số liệu CloudWatch Metrics Strategies to trigger automated scale-out and scale-in events based on CloudWatch metrics
Target Tracking Scaling (Dễ & Khuyên dùng nhất)
Bạn chỉ định một chỉ số mục tiêu cụ thể, ASG tự động tính toán tăng hoặc giảm số máy để duy trì chỉ số đó ổn định. Ví dụ: "Giữ mức CPU trung bình toàn cụm ở mức 50%" hoặc "Giữ số lượng request mỗi target ở mức 1000".
Khuyên dùngĐơn giản nhấtAvg CPU / Request Count
Specify a target metric value, and ASG continuously adjusts instance counts up and down to match that target. Examples: "Maintain average fleet CPU at 50%" or "ALBRequestCountPerTarget at 1000".
RecommendedHands-offAvg CPU / Target Requests
Step Scaling (Co giãn theo từng bậc tải)
Co giãn linh hoạt dựa trên các mức ngưỡng cảnh báo của CloudWatch Alarm. Ví dụ:
  • Nếu CPU từ 70% đến 85%: Thêm 2 máy chủ (+2).
  • Nếu CPU vượt quá 85%: Bổ sung khẩn cấp 5 máy chủ (+5).
  • Nếu CPU tụt xuống dưới 30%: Giảm 1 máy chủ (-1).
Stepwise adjustments responding directly to CloudWatch alarm thresholds. Example:
  • If CPU 70%–85%: Add 2 instances (+2).
  • If CPU > 85%: Add 5 instances (+5).
  • If CPU < 30%: Remove 1 instance (-1).
Scheduled Scaling (Co giãn theo lịch trình đặt trước)
Dành cho các sự kiện có chu kỳ hoặc thời gian biết trước. Ví dụ: "Tự động tăng Desired Capacity lên 20 máy chủ vào lúc 8:00 sáng Thứ Sáu (Black Friday) và giảm về 4 máy chủ vào 22:00 tối Chủ Nhật".

For predictable cyclical traffic spikes. Example: "Scale out to 20 instances every Friday morning at 08:00 AM (e.g. Flash Sales) and scale back down Sunday night at 22:00 PM".

AWS tự động phân tích dữ liệu lịch sử tải của hệ thống trong quá khứ thông qua mô hình Machine Learning, từ đó khởi tạo máy chủ trước 1 khoảng thời gian chuẩn bị để đón đầu cơn sóng truy cập thực tế.

6. Các bẫy & Kịch bản đề thi thường gặp (SAA-C03 Exam Traps) 6. Common Exam Traps & Scenarios (SAA-C03)
Tổng hợp các câu hỏi tình huống kinh điển về cân bằng tải và co giãn trong đề thi Canonical situational questions and trick patterns tested in SAA-C03
Khách hàng yêu cầu Cố định IP để Whitelist Tường lửa
• Vấn đề: Khách hàng doanh nghiệp yêu cầu một hoặc vài địa chỉ IP tĩnh để cấu hình mở tường lửa (Firewall Whitelisting).
• Giải pháp: Bắt buộc dùng Network Load Balancer (NLB) vì NLB gán 1 Static Public IP (hoặc gán Elastic IP) trên mỗi AZ. ALB KHÔNG có IP tĩnh (IP của ALB thay đổi ngẫu nhiên theo thời gian, chỉ có DNS Name).
• Scenario: Corporate clients require fixed static IP addresses to configure on-premises firewall whitelisting.
• Solution: Always choose Network Load Balancer (NLB) because NLB assigns fixed static Elastic IPs per AZ. ALB does not support static IPs (ALB resolves to rotating dynamic IPs via DNS).
Lấy địa chỉ IP thật của người dùng (Client IP Preservation)
• Khi dùng ALB, gói tin gửi tới EC2 có nguồn là IP riêng của chính ALB. Để lấy được IP công khai của Client, ứng dụng phải đọc header HTTP X-Forwarded-For.
• Các header khác kèm theo: X-Forwarded-Proto (giao thức http hay https), X-Forwarded-Port (cổng truy cập ban đầu).
• Với NLB: Client IP được bảo toàn tự nhiên ở tầng TCP nếu target là instance ID.
• With ALB, backend instances see the ALB's private IP as the request source. To retrieve true user IP, inspect the X-Forwarded-For header.
• Supplementary headers: X-Forwarded-Proto (client protocol), X-Forwarded-Port.
• With NLB: Client IP is natively preserved at the TCP packet level when targeting instance IDs.
Co giãn ASG theo độ dài hàng đợi SQS (Backlog per Instance)
• Đề bài: "Ứng dụng đọc message từ hàng đợi SQS, cần co giãn số máy chủ theo tải tin nhắn tồn đọng".
• Bẫy thường gặp: Chỉ theo dõi số tin nhắn ApproximateNumberOfMessages là chưa đủ vì khi máy chủ tăng lên, hàng đợi vẫn có thể chưa giảm ngay.
• Đáp án chuẩn: Tạo Custom CloudWatch Metric: Số tin nhắn chia cho số instance hiện tại (Backlog per Instance) và dùng Target Tracking.
• Scenario: "Application workers consume messages from SQS queue; need responsive auto-scaling".
• Trap: Scaling strictly on raw ApproximateNumberOfMessages causes severe over-provisioning.
• Canonical Answer: Publish a Custom CloudWatch Metric: Queue Backlog per Instance (Queue Size / Active Worker Count) and scale via Target Tracking.
ASG Lifecycle Hooks & Thu thập Log trước khi xóa máy
• Khi ASG quyết định Terminate 1 máy chủ, máy sẽ bị xóa ngay lập tức và toàn bộ log trong RAM/Instance Store sẽ biến mất.
• Để ngăn việc này: Thiết lập ASG Lifecycle Hook tại sự kiện autoscaling:EC2_INSTANCE_TERMINATING. Trạng thái máy sẽ dừng ở Terminating:Wait cho phép bạn chạy script nén log và đẩy lên S3 trước khi instance bị tiêu hủy hoàn toàn.
• By default, scale-in terminates instances immediately, losing ephemeral local logs.
• Solution: Configure an ASG Lifecycle Hook for EC2_INSTANCE_TERMINATING. Transitions state to Terminating:Wait, enabling scripts to flush logs to S3 before final destruction.

7. Nguyên tắc vàng khi làm bài thi (SAA-C03 Golden Rules) 7. SAA-C03 Exam Golden Rules
Bộ quy tắc bất biến giúp loại trừ ngay các đáp án sai trong đề thi chứng chỉ Essential axioms to rapidly eliminate incorrect choices in the exam
  • 1
    ALB luôn có DNS Name, KHÔNG BAO GIỜ gán IP tĩnh ALB operates exclusively on DNS Names, NEVER on Static IPs Bất kỳ đáp án nào đề cập đến việc gán Elastic IP cho Application Load Balancer hoặc cung cấp IP tĩnh cố định từ ALB đều là đáp án SAI. Khi cần IP tĩnh, đáp án bắt buộc phải là Network Load Balancer (NLB) hoặc kết hợp AWS Global Accelerator. Any answer suggesting assigning Elastic IPs directly to an ALB is always WRONG. When static entrypoint IPs are required, choose Network Load Balancer (NLB) or front with AWS Global Accelerator.
  • 2
    Bảo mật EC2 backend: Chỉ mở port từ Security Group của chính Load Balancer Backend Security: Only allow traffic originating from the Load Balancer's Security Group Không bao giờ mở cổng 80/443 của máy chủ EC2 backend ra 0.0.0.0/0. Nguyên tắc vàng là cấu hình Inbound Rule của EC2 Security Group: Source = ID của Security Group gắn trên Load Balancer. Never expose EC2 backend ports to 0.0.0.0/0. The canonical security architecture sets Inbound Rule: Source = Security Group ID of the Load Balancer.
  • 3
    Tự động phát hiện lỗi tầng ứng dụng: Luôn bật ELB Health Check trên ASG Detect application-level crashes: Always enable ELB Health Checks on ASG Mặc định ASG chỉ kiểm tra phần cứng EC2. Nếu ứng dụng web bị đơ (crash), ASG mặc định sẽ không biết. Phải đổi sang Health Check Type = ELB để ASG tự động thay thế instance khi nó trả về lỗi HTTP Unhealthy. ASG default checks only verify VM hardware status. To auto-heal web applications that freeze or throw HTTP 500s, switch ASG Health Check Type to ELB.
  • !
    Cắt giảm tới 90% chi phí ASG: Kết hợp Spot Instances bằng Launch Template Cut ASG costs up to 90%: Combine Spot Instances via Launch Templates Đối với các tải xử lý hàng loạt, kiến trúc không trạng thái (Stateless), giải pháp tối ưu chi phí đỉnh cao nhất trong đề thi là cấu hình Auto Scaling Group sử dụng Launch Template với chiến lược hỗn hợp: một lượng On-Demand Instances làm cốt lõi và bổ sung Spot Instances cho phần tải co giãn. For batch processing and stateless resilient tiers, the ultimate cost-optimization pattern is using Launch Templates with mixed instance types: a baseline of On-Demand backed by Spot Instances for elastic spikes.
