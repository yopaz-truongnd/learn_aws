  • Bẫy 2 — Bộ nhớ dùng chung HPC: FSx for Lustre: Để đạt hàng triệu IOPS và thông lượng hàng trăm GB/s cho tính toán song song, Machine Learning và mô phỏng tài chính, chọn Amazon FSx for Lustre. Trap 2 — HPC Shared Storage: FSx for Lustre: For millions of IOPS and hundreds of GB/s throughput for parallel processing, Machine Learning, and financial simulations, choose Amazon FSx for Lustre. Lustre seamlessly reads directly from and writes back to Amazon S3.
  • Bẫy 3 — Chiến lược Caching: Cache-Aside vs Write-Through: Cache-Aside (Lazy Loading) chỉ nạp dữ liệu vào cache khi có Cache Miss (tiết kiệm bộ nhớ cache, nhưng có thể đọc dữ liệu cũ - Stale Data). Write-Through ghi đồng thời vào DB và Cache (dữ liệu trong cache luôn mới nhất, nhưng tốn dung lượng lưu dữ liệu ít đọc). Trap 3 — Caching Strategies: Cache-Aside vs Write-Through: Cache-Aside (Lazy Loading) only loads into cache on a cache miss (saves memory, but risks stale reads). Write-Through writes to DB and Cache simultaneously (cache is never stale, but incurs overhead caching rarely read data).
  • Bẫy 4 — Placement Groups: Cluster vs Spread vs Partition: Cluster gom các EC2 vào cùng 1 rack trong 1 AZ để đạt độ trễ mạng thấp nhất (dùng cho HPC, Big Data). Spread đặt mỗi EC2 trên rack phần cứng riêng biệt (tối đa 7 instances/AZ) để tối đa khả năng chịu lỗi phần cứng. Partition chia nhỏ thành nhiều phân vùng cho HDFS/Hadoop/Cassandra. Trap 4 — Placement Groups: Cluster vs Spread vs Partition: Cluster packs instances onto the same rack within 1 AZ for lowest latency (HPC, Big Data). Spread places each instance on separate hardware racks (max 7 instances/AZ) for fault isolation. Partition divides partitions for HDFS/Hadoop/Cassandra.

1. High-Performance Computing (HPC) on AWS
Giải pháp cho các bài toán mô phỏng vật lý, tài chính và Machine Learning Solutions for physics simulation, financial modeling & AI/ML workloads
Định nghĩa & Thách thức HPC:
Workload tính toán hiệu năng cao đòi hỏi hàng ngàn CPU/GPU chạy song song kết nối với nhau với độ trễ mạng thấp nhất có thể (micro-seconds) và hệ thống file chia sẻ thông lượng cực lớn. HPC workloads demand thousands of parallel CPUs/GPUs communicating with ultra-low microsecond network latency and high-throughput shared storage.
Thành phần Mạng & Tính toán cốt lõi:
1. Cluster Placement Group: Đặt các máy chủ trong cùng một rack phần cứng ở 1 AZ duy nhất để đạt độ trễ mạng thấp nhất.
2. Elastic Fabric Adapter (EFA): Card mạng chuyên dụng cho phép giao tiếp node-to-node thông qua chuẩn MPI (Message Passing Interface), bỏ qua tầng OS kernel để đạt tốc độ truyền tải tối đa.
3. AWS Batch: Dịch vụ quản lý hàng đợi và lập lịch chạy hàng chục ngàn container/job tính toán tự động dựa trên EC2 Spot Instances để tối ưu chi phí. 1. Cluster Placement Group: Packs instances close together inside 1 AZ for minimum network latency.
2. Elastic Fabric Adapter (EFA): Specialized network interface enabling node-to-node MPI communication by bypassing OS kernel stack.
3. AWS Batch: Fully managed batch computing scheduler provisioning Spot EC2 instances dynamically to optimize batch job costs.
Lưu trữ cho HPC (Storage Layer):
Amazon FSx for Lustre là lựa chọn số 1 cho HPC. Tương thích chuẩn POSIX, mở rộng thông lượng lên đến hàng trăm GB/s, và có khả năng đọc/ghi trực tiếp và trong suốt với Amazon S3. Amazon FSx for Lustre is the #1 choice for HPC. POSIX-compliant, scales throughput to hundreds of GB/s, with seamless transparent bi-directional sync with Amazon S3.
Bẫy đề thi / Exam Traps:
⚠️ EFA chỉ hỗ trợ trên Linux (không hỗ trợ Windows).
⚠️ Không thể gom các instance trải dài trên nhiều Availability Zones vào một Cluster Placement Group. ⚠️ EFA is supported on Linux only (not available for Windows).
⚠️ You cannot span a single Cluster Placement Group across multiple Availability Zones.

2. Multi-Tier Caching Architecture
Tối ưu hóa độ trễ phản hồi từ rìa mạng đến cơ sở dữ liệu Optimizing response latencies from edge to database layer
Các tầng Caching trong AWS:
1. Edge Cache (CloudFront): Lưu trữ nội dung tĩnh và động gần người dùng nhất trên toàn cầu.
2. API Gateway Cache: Lưu trữ kết quả phản hồi của API endpoint trong một khoảng thời gian TTL.
3. In-Memory Cache (ElastiCache Redis / Memcached): Lưu trữ kết quả truy vấn cơ sở dữ liệu quan hệ (RDS/Aurora).
4. DynamoDB Accelerator (DAX): In-memory cache chuyên dụng cho DynamoDB giảm độ trễ từ milliseconds xuống microseconds. 1. Edge Cache (CloudFront): Caches static/dynamic web assets globally close to end-users.
2. API Gateway Cache: Caches API endpoint responses with configurable TTLs.
3. In-Memory Cache (ElastiCache Redis/Memcached): Caches relational DB query results in RAM.
4. DynamoDB Accelerator (DAX): Dedicated in-memory cache for DynamoDB reducing read latency to microseconds.
Chiến lược Caching cơ bản:
1. Cache-Aside (Lazy Loading): Ứng dụng đọc từ cache → Nếu Cache Miss thì đọc từ DB → Ghi ngược vào Cache. Tiết kiệm RAM nhưng lần đọc đầu bị trễ.
2. Write-Through: Khi cập nhật dữ liệu, ứng dụng ghi đồng thời vào DB và Cache. Dữ liệu luôn đồng nhất nhưng tốn tài nguyên cache cho dữ liệu ít đọc. 1. Cache-Aside (Lazy Loading): App reads cache → On cache miss, reads DB → Populates cache. Saves RAM, but initial read incurs latency.
2. Write-Through: Writes to DB and Cache simultaneously. Data is never stale, but caches rarely read records.
Redis vs Memcached:
Chọn ElastiCache Redis khi cần: Cấu trúc dữ liệu nâng cao (sets, sorted sets, hashes, pub/sub), lưu trữ bền vững (Persistence / AOF / RDB), tự động failover đa AZ, và mã hóa.
Chọn Memcached khi chỉ cần: Bộ nhớ đệm key-value đơn giản, thuần in-memory và hỗ trợ đa luồng (multi-threaded). Choose ElastiCache Redis when you need: Advanced data structures (sets, sorted sets, pub/sub), persistence/snapshots, multi-AZ auto failover, and encryption.
Choose Memcached when you need: Simple key-value caching, pure in-memory performance, and multi-threading.
Bẫy đề thi / Exam Traps:
⚠️ DAX là in-memory cache chỉ dành riêng cho DynamoDB. Không thể dùng DAX cho Aurora hay RDS! Với Aurora/RDS, luôn dùng ElastiCache. ⚠️ DAX is an in-memory cache exclusively built for DynamoDB. Cannot be used with Aurora or RDS! For relational databases, always use ElastiCache.

3. Microservices & Event-Driven Decoupling
Phân tách vi dịch vụ và xử lý bất đồng bộ quy mô lớn Microservices decoupling and large-scale asynchronous event handling
Khái niệm Phân tách (Loose Coupling):
Thiết kế hệ thống sao cho sự cố hoặc quá tải ở một dịch vụ (ví dụ: Tải ảnh sản phẩm) không làm sập các dịch vụ khác (ví dụ: Thanh toán giỏ hàng). Sử dụng Message Brokers (SQS, SNS, EventBridge) làm vùng đệm trung gian. Architectural pattern ensuring failure or traffic spikes in one microservice (e.g. image processing) does not cascade to others (e.g. checkout). Employs message brokers (SQS, SNS, EventBridge) as buffers.
Mẫu kiến trúc SNS Fan-Out:
Khi có đơn hàng mới được tạo, đẩy message vào SNS Topic. SNS tự động sao chép thông điệp (Fan-out) sang nhiều SQS Queues độc lập: Queue 1 cho dịch vụ trừ kho (Inventory), Queue 2 cho dịch vụ xuất hóa đơn (Invoicing), Queue 3 cho dịch vụ gửi email xác nhận (SES). Mỗi worker pool scale độc lập. On new order creation, publish message to an SNS Topic. SNS automatically fans out to multiple independent SQS Queues: Queue 1 for inventory, Queue 2 for invoicing, Queue 3 for email notifications. Each worker pool scales independently.
SQS FIFO với Message Group ID:
Đảm bảo thứ tự xử lý thông điệp chính xác theo từng khách hàng (Customer ID làm MessageGroupId). Các thông điệp cùng khách hàng được xử lý tuần tự, trong khi các khách hàng khác nhau được xử lý song song bởi nhiều worker! Guarantees strict ordered processing per customer (Customer ID as MessageGroupId). Messages within the same group are processed strictly in-order, while distinct customer groups process in parallel across workers!
Bẫy đề thi / Exam Traps:
⚠️ Nếu subscriber là HTTPS endpoint hoặc email → Đẩy trực tiếp từ SNS. Nhưng nếu subscriber cần lưu trữ thông điệp khi hệ thống bận → Bắt buộc kết hợp SNS → SQS Queue → EC2/Lambda. ⚠️ If subscriber is HTTPS or email → Push directly from SNS. But if workers need queuing/buffering during load spikes → Must use SNS → SQS → EC2/Lambda fan-out.

4. AWS Global Accelerator vs CloudFront
Định tuyến mạng toàn cầu tối ưu hóa hiệu năng và độ tin cậy Global traffic acceleration for performance and high availability
Định nghĩa & Bản chất:
1. AWS Global Accelerator: Dịch vụ mạng định tuyến lưu lượng người dùng qua mạng cáp quang toàn cầu của AWS thông qua 2 địa chỉ Anycast Static IPv4 tĩnh.
2. Amazon CloudFront: Mạng phân phối nội dung (CDN) lưu trữ bộ đệm (Caching) cho nội dung web tĩnh và động tại Edge Locations. 1. AWS Global Accelerator: Networking service routing user traffic over AWS global private fiber network using 2 static Anycast IPv4 addresses.
2. Amazon CloudFront: Content Delivery Network (CDN) caching static and dynamic web content at Edge Locations.
Giao thức hỗ trợ (Protocol Support):
1. CloudFront: Chỉ hỗ trợ giao thức web HTTP / HTTPS và WebSockets.
2. Global Accelerator: Hỗ trợ cả TCP và UDP (phù hợp cho game online, IoT, VoIP, video streaming trực tiếp, DNS, non-HTTP applications). 1. CloudFront: Optimized strictly for HTTP / HTTPS web traffic and WebSockets.
2. Global Accelerator: Supports both TCP and UDP (ideal for gaming, IoT, VoIP, live streaming, DNS, non-HTTP applications).
Cơ chế Failover đa vùng:
Global Accelerator thực hiện Health Check liên tục tới các Endpoint Groups ở các Region khác nhau. Khi một Region gặp sự cố, Global Accelerator tự động chuyển hướng lưu lượng trong vòng 1 phút mà không phụ thuộc vào thời gian TTL của DNS client! Global Accelerator continuously runs health checks across regional Endpoint Groups. If a region fails, it automatically shifts traffic within 1 minute, completely bypassing client DNS caching/TTL issues!
Bẫy đề thi / Exam Traps:
⚠️ Đề thi yêu cầu: "Cần 2 địa chỉ IP tĩnh cố định cho khách hàng whitelist trên tường lửa doanh nghiệp và tăng tốc ứng dụng UDP" → Bắt buộc chọn AWS Global Accelerator!
⚠️ Đề thi yêu cầu: "Giảm tải cho máy chủ bằng cách lưu cache video và hình ảnh" → Chọn CloudFront. ⚠️ Question asks: "Need 2 fixed static IPs to whitelist on corporate firewalls and accelerate UDP application" → Must choose AWS Global Accelerator!
⚠️ Question asks: "Offload origin servers by caching videos and images" → Choose CloudFront.

  • Không bao giờ chọn Spread Placement Group cho HPC: Spread phân tán instances trên các rack khác nhau để tăng độ an toàn, điều này làm tăng độ trễ mạng! HPC luôn dùng Cluster Placement Group.
  • Lustre kết nối S3: FSx for Lustre đồng bộ trực tiếp với S3. Bạn có thể tạo Lustre filesystem từ dữ liệu trong S3, chạy tính toán siêu nhanh, và đồng bộ kết quả ngược lại S3 rồi xóa Lustre để tiết kiệm tiền.
  • ENA vs EFA: ENA tăng tốc mạng chuẩn IP; EFA dùng giao thức SRD (Scalable Reliable Datagram) bypass Linux kernel dành riêng cho ứng dụng MPI phân tán.
💡 QUY TẮC VÀNG THIẾT KẾ PHÂN TÁN 💡 DISTRIBUTED DESIGN RULES
  • Stateless Web Servers: Lưu trữ Session State trong Amazon ElastiCache (Redis) hoặc DynamoDB để người dùng có thể kết nối tới bất kỳ EC2 nào phía sau ALB mà không mất phiên làm việc.
  • Bảo vệ Database khỏi đợt sóng tải (Spikes): Đặt SQS Queue ở giữa API và Worker để lưu trữ tạm các yêu cầu ghi dữ liệu; worker đọc từ SQS và ghi tuần tự vào Database.
  • Zero Latency Writes với Aurora Global Database: Đọc dữ liệu cục bộ với độ trễ < 1 giây tại secondary regions, ghi dữ liệu về primary region tự động.
