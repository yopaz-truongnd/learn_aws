2. Bài thực hành 1: Thao tác hàng đợi Amazon SQS qua AWS CLI 2. Hands-On 1: Operating Amazon SQS Queues via AWS CLI
Tệp nguồn: aws_document/sqs/sqs.sh Source file: aws_document/sqs/sqs.sh
Mã nguồn trong aws_document/sqs/sqs.sh Source code in aws_document/sqs/sqs.sh
# 1. Liệt kê tất cả các hàng đợi SQS trong Region us-east-1: aws sqs list-queues --region us-east-1 # 2. Gửi một tin nhắn (Producer) vào hàng đợi MyFirstQueue: aws sqs send-message \ --queue-url https://queue.amazonaws.com/387124123361/MyFirstQueue \ --region us-east-1 \ --message-body hello-world # 3. Nhận tin nhắn (Consumer) kèm Visibility Timeout (30s) và Long Polling (20s): aws sqs receive-message \ --region us-east-1 \ --queue-url https://queue.amazonaws.com/387124123361/MyFirstQueue \ --max-number-of-messages 10 \ --visibility-timeout 30 \ --wait-time-seconds 20 # 4. Xóa tin nhắn khỏi hàng đợi sau khi xử lý xong bằng ReceiptHandle: aws sqs delete-message \ --receipt-handle "AQEBB+moMioWDaeaCZguaiMPXEqDe6n4..." \ --queue-url https://queue.amazonaws.com/387124123361/MyFirstQueue \ --region us-east-1
Giải thích 4 tham số quyết định trong đề thi SAA-C03 4 Critical Parameters Tested in SAA-C03
--visibility-timeout 30 (Thời gian ẩn tạm thời)
Khi một Consumer gọi receive-message, tin nhắn vẫn nằm trong SQS nhưng bị ẩn đi trong 30 giây để các Consumer khác không lấy trùng. Nếu sau 30 giây mà Consumer chưa gọi delete-message, tin nhắn sẽ hiện trở lại trong hàng đợi để xử lý lại!
When a Consumer calls receive-message, the message stays in SQS but becomes invisible for 30 seconds to prevent duplicate processing. If delete-message is not called within 30s, the message reappears in the queue!
--wait-time-seconds 20 (SQS Long Polling)
Kích hoạt Long Polling (tối đa 20 giây): Nếu hàng đợi đang trống, lệnh CLI sẽ kiên nhẫn chờ tối đa 20 giây cho đến khi có tin nhắn mới tới rồi mới trả về. Giúp giảm số lượng API calls rỗng và tiết kiệm chi phí SQS.
Enables Long Polling (max 20 seconds): If the queue is empty, the request waits up to 20 seconds for a message to arrive before returning, reducing empty API responses and lowering SQS costs.
--max-number-of-messages 10 (Giới hạn Batch)
Mỗi lần gọi receive-message có thể lấy tối đa 10 tin nhắn cùng lúc (tổng kích thước mỗi tin tối đa 256 KB).
Each receive-message call can retrieve a batch of up to 10 messages at once (maximum 256 KB per message).
--receipt-handle vs MessageId (Bẫy thực hành!)
Để xóa tin nhắn bằng delete-message, bạn bắt buộc phải truyền ReceiptHandle (mã biên nhận sinh ra ở lần receive-message gần nhất), KHÔNG phải MessageId!
To delete a message via delete-message, you MUST pass the ReceiptHandle returned by the latest receive-message call, NOT the MessageId!

#!/bin/bash aws --version # ================= PRODUCER ================= # AWS CLI v2 (Bắt buộc có cờ --cli-binary-format raw-in-base64-out): aws kinesis put-record --stream-name test --partition-key user1 --data "user signup" --cli-binary-format raw-in-base64-out # AWS CLI v1: aws kinesis put-record --stream-name test --partition-key user1 --data "user signup" # ================= CONSUMER ================= # Bước 1: Kiểm tra thông tin Stream và lấy danh sách Shard ID: aws kinesis describe-stream --stream-name test # Bước 2: Lấy con trỏ đọc dữ liệu (Shard Iterator) từ đầu luồng (TRIM_HORIZON): aws kinesis get-shard-iterator --stream-name test --shard-id shardId-000000000000 --shard-iterator-type TRIM_HORIZON # Bước 3: Đọc bản ghi bằng mã ShardIterator vừa nhận được: aws kinesis get-records --shard-iterator <PASTE_SHARD_ITERATOR_HERE>
Các bước thực hành & Giải thích chi tiết Step-by-Step Guide & Detailed Explanation
  • 1
    Tạo Kinesis Data Stream tên test Create a Kinesis Data Stream Named test Vào Kinesis Console → Data streams → Create data stream, đặt tên là test, chọn chế độ Provisioned với 1 Shard (1 MB/s hoặc 1000 records/s chiều ghi; 2 MB/s chiều đọc) để kiểm soát chi phí thực hành. In Kinesis Console → Data streams → Create data stream, name it test and select Provisioned mode with 1 Shard (1 MB/s or 1000 records/s write; 2 MB/s read).
  • 2
    Ý nghĩa của --partition-key user1 và --cli-binary-format Understanding --partition-key user1 and --cli-binary-format • Kinesis băm (MD5 hash) giá trị PartitionKey (user1) để quyết định bản ghi sẽ đi vào Shard nào. Nhờ đó, mọi sự kiện của cùng một user1 luôn nằm trong cùng 1 Shard và được đảm bảo đúng thứ tự (Ordering per Partition Key)!
    • Trên AWS CLI v2, mọi tham số kiểu blob mặc định yêu cầu đầu vào đã mã hóa base64; thêm cờ --cli-binary-format raw-in-base64-out giúp bạn truyền chuỗi văn bản thuần "user signup" trực tiếp.     • Kinesis hashes the PartitionKey (user1) via MD5 to route records to a specific Shard, guaranteeing strict ordering per Partition Key!
    • On AWS CLI v2, binary parameters expect base64 input by default; --cli-binary-format raw-in-base64-out lets you pass raw strings like "user signup" directly.
  • 3
    Ý nghĩa của TRIM_HORIZON vs LATEST khi lấy Shard Iterator TRIM_HORIZON vs LATEST Shard Iterator Types • TRIM_HORIZON: Bắt đầu đọc từ bản ghi cũ nhất hiện còn lưu trong Shard (như tua lại băng từ đầu).
    • LATEST: Chỉ đọc các bản ghi mới phát sinh kể từ thời điểm gọi lệnh.
    • Khi nhận kết quả từ get-records, trường Data sẽ ở dạng Base64 (ví dụ dXNlciBzaWdudXA= → giải mã ra user signup), đồng thời trả về NextShardIterator để đọc tiếp vòng sau.     • TRIM_HORIZON: Starts reading from the oldest untrimmed record in the Shard (replay from beginning).
    • LATEST: Reads only new records arriving after the iterator is created.
    • The get-records output returns Base64-encoded Data (dXNlciBzaWdudXA= → decodes to user signup) along with NextShardIterator for continuous polling.
