2. Phân tích Script User Data tự động tương thích IMDSv1 & IMDSv2 2. Analyzing the IMDSv1 & IMDSv2 Compatible User Data Script
Tệp nguồn: aws_document/route53/user-data.sh Source file: aws_document/route53/user-data.sh
Mã nguồn trong aws_document/route53/user-data.sh Source code in aws_document/route53/user-data.sh
#!/bin/bash yum update -y yum install -y httpd systemctl start httpd systemctl enable httpd # updated script to make it work with Amazon Linux 2023 CHECK_IMDSV1_ENABLED=$(curl -s -o /dev/null -w "%{http_code}" http://169.254.169.254/latest/meta-data/) if [[ "$CHECK_IMDSV1_ENABLED" -eq 200 ]] then EC2_AVAIL_ZONE="$(curl -s http://169.254.169.254/latest/meta-data/placement/availability-zone)" else EC2_AVAIL_ZONE="$(TOKEN=`curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600"` && curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone)" fi echo "<h1>Hello world from $(hostname -f) in AZ $EC2_AVAIL_ZONE </h1>" > /var/www/html/index.html
Giải thích cơ chế hoạt động của Script How the Script Works Under the Hood
Kiểm tra trạng thái IMDSv1 bằng HTTP Status Code
Lệnh curl -s -o /dev/null -w "%{http_code}" gửi một request GET không kèm token tới 169.254.169.254/latest/meta-data/ và chỉ lấy mã HTTP trả về:
• Nếu trả về 200: Máy chủ đang cho phép IMDSv1.
• Nếu trả về 401: Máy chủ bắt buộc dùng IMDSv2 (mặc định trên Amazon Linux 2023).
curl -s -o /dev/null -w "%{http_code}" sends a tokenless GET request to 169.254.169.254/latest/meta-data/ and extracts the HTTP status code:
• 200: IMDSv1 is enabled.
• 401: IMDSv2 is required (default on Amazon Linux 2023).
Nhánh else: Lấy Session Token IMDSv2
Khi IMDSv1 bị tắt, script gọi PUT http://169.254.169.254/latest/api/token với header X-aws-ec2-metadata-token-ttl-seconds: 21600 (token sống trong 6 giờ), lưu vào biến $TOKEN rồi đính kèm header X-aws-ec2-metadata-token: $TOKEN để lấy tên Availability Zone (placement/availability-zone).
When IMDSv1 is disabled, the script sends a PUT request with X-aws-ec2-metadata-token-ttl-seconds: 21600 (6-hour TTL) to obtain $TOKEN, then passes X-aws-ec2-metadata-token: $TOKEN to fetch placement/availability-zone.

3. Các bước thực hành kiểm thử các Routing Policies trên Route 53 3. Step-by-Step Guide to Testing Route 53 Routing Policies
Tạo 2-3 máy chủ EC2 ở các Region khác nhau và cấu hình bản ghi A trên Route 53 Launch 2-3 EC2 instances across different Regions and configure Route 53 A records
  • 1
    Khởi tạo 2 hoặc 3 EC2 Instances ở các Region khác nhau Launch 2 or 3 EC2 Instances in Different Regions Tạo các máy chủ t2.micro / t3.micro tại us-east-1 (N. Virginia), eu-central-1 (Frankfurt) và ap-southeast-1 (Singapore). Mở cổng HTTP 80 trong Security Group và dán nội dung file aws_document/route53/user-data.sh vào ô User data của từng máy. Launch t2.micro / t3.micro instances in us-east-1, eu-central-1, and ap-southeast-1. Allow HTTP Port 80 in each Security Group and paste aws_document/route53/user-data.sh into each instance's User data.
  • 2
    Kiểm thử Weighted Routing Policy (Phân phối theo trọng số) Test Weighted Routing Policy Trong Route 53 Public Hosted Zone, tạo 3 bản ghi kiểu A cùng tên (ví dụ weighted.yourdomain.com), chọn Routing policy: Weighted, đặt TTL = 3 giây, và gán Weight lần lượt là 70, 20, 10 (với Record ID khác nhau). Khi làm mới trình duyệt hoặc chạy dig weighted.yourdomain.com sau khi hết TTL, bạn sẽ thấy trang web đổi giữa các AZ theo đúng tỷ lệ! In your Route 53 Public Hosted Zone, create 3 A records with the same name (e.g., weighted.yourdomain.com), select Routing policy: Weighted, set TTL = 3 seconds, and assign weights 70, 20, 10 with unique Record IDs. Refreshing after TTL expiry rotates responses across AZs!
  • 3
    Kiểm thử Latency & Failover Routing Policy (Kèm Health Check) Test Latency & Failover Routing Policies (With Health Checks) • Tạo một Route 53 Health Check kiểm tra cổng 80 đường dẫn / của máy chủ ở us-east-1.
    • Tạo 2 bản ghi Failover: máy us-east-1 làm Primary (gắn Health Check) và máy ap-southeast-1 làm Secondary.
    • Thử tắt dịch vụ Apache trên máy Primary (sudo systemctl stop httpd) → sau khoảng 1-2 phút Health Check chuyển sang Unhealthy, toàn bộ truy cập sẽ tự động chuyển hướng sang máy chủ ở Singapore (ap-southeast-1)!     • Create a Route 53 Health Check monitoring HTTP port 80 path / on your us-east-1 instance.
    • Create 2 Failover records: us-east-1 as Primary (associated with the Health Check) and ap-southeast-1 as Secondary.
    • Stop Apache on Primary (sudo systemctl stop httpd) → once the Health Check turns Unhealthy, traffic automatically fails over to ap-southeast-1!
